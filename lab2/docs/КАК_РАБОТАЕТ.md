## 1. Что получилось

В проекте четыре исполняемых файла и три версии одной программы:

```text
app/main.c, app/funcs.c
    ├── build/app-static    — библиотеки вшиты в файл
    ├── build/app-dynamic   — библиотеки открываются через dlopen
    └── build/app-blob      — ELF-файл без собственной libc и без DT_NEEDED

elfloader/              → build/elfloader
```

### `app-static`

Обычная программа, слинкованная с тремя статическими архивами:

```text
libfreetype.a + libpng.a + libz.a
```

Код библиотек становится частью исполняемого файла. При запуске этих
трёх `.so` в системе может не быть вообще.

### `app-dynamic`

Тот же код рисования, но библиотеки не указаны в команде компоновки.
В начале `main` вызывается `load_libraries()`, которая делает
`dlopen` для `libz.so.1`, `libpng.so` и `libfreetype.so`, а затем
`dlsym` для каждой нужной функции. Время этой работы измеряется
отдельно и печатается как `load`.

### `app-blob`

ELF-файл, собранный без стандартной библиотеки:

```text
-nostdlib -pie -fPIE
```

У него нет `main`, нет `_start` и нет `DT_NEEDED`. Точка входа —
`blob_entry`, её адрес записан в заголовок ELF. Внутри файла лежат
все три библиотеки, но все обращения к libc заменены на вызовы через
таблицу указателей, которую заполняет загрузчик.

### `elfloader`

Обычная программа, которая:

- открывает blob-файл;
- читает его ELF-заголовок;
- отображает сегменты `PT_LOAD` в память;
- применяет релокации `R_X86_64_RELATIVE`;
- заполняет таблицу функций libc;
- вызывает `blob_entry` с параметрами;
- освобождает память.

Исходники самого загрузчика взяты из `erincandescent/elfload`, а
`elfloader/main.c` — тонкая обёртка над этой библиотекой.

## 2. Быстрый запуск

Сборка всего:

```bash
cd lab2
make clean
make all
```

Отдельные цели:

```bash
make static
make dynamic
make blob
```

Запуск:

```bash
./build/app-static  font.ttf out-static.png  "TRSPO"
./build/app-dynamic font.ttf out-dynamic.png "TRSPO"
./build/elfloader build/app-blob font.ttf out-blob.png "TRSPO"
```

Пример вывода:

```text
load: 0.000000 s
zlib 1.2.11
total: 0.002647 s

load: 0.003464 s
zlib 1.2.11
total: 0.004435 s

load: 0.000000 s
zlib 1.2.11
total: 0.000903 s
```

Все три PNG должны совпасть побайтово:

```bash
sha256sum out-static.png out-dynamic.png out-blob.png
```

```text
e8bcbb...b791cf0  out-static.png
e8bcbb...b791cf0  out-dynamic.png
e8bcbb...b791cf0  out-blob.png
```

Очистка:

```bash
make clean
```

Она удаляет `build/`, объектные файлы приложения и объектные каталоги
библиотек.

## 3. Ключевые понятия

### Этапы сборки

Сборка программы на C состоит из четырёх шагов:

```text
main.c
  │ препроцессор  (cpp)         — #include, #define, #ifdef
  ▼
main.i
  │ компилятор    (cc1)         — C → ассемблер
  ▼
main.s
  │ ассемблер     (as)          — ассемблер → объектный файл
  ▼
main.o
  │ компоновщик   (ld)          — объектные файлы → исполняемый файл
  ▼
app
```

`make` не делает эту работу сам. Он только вызывает `gcc`, а `gcc`
уже запускает нужные этапы. Например, команда

```bash
gcc -c funcs.c -o funcs.o
```

останавливается на объектном файле, а

```bash
gcc -o app main.o funcs.o libz.a
```

запускает компоновщик.

### Объектный файл и символы

Объектный файл `.o` содержит:

- машинный код функций;
- данные;
- таблицу символов;
- **неразрешённые ссылки** на внешние функции и переменные.

Например, `funcs.o` после компиляции содержит:

```text
U FT_Init_FreeType
U FT_New_Face
U png_create_write_struct
U png_write_image
U zlibVersion
T render_png
```

`U` — undefined, `T` — определённая функция в секции `.text`. На
этапе компоновки все `U` должны стать известными адресами. Если
какая-то ссылка осталась неразрешённой, компоновщик печатает
`undefined reference`.

### Статическая библиотека

`.a` — это просто архив объектных файлов:

```text
libz.a
  ├── adler32.o
  ├── crc32.o
  ├── deflate.o
  ├── inflate.o
  └── ...
```

Компоновщик просматривает архив не целиком, а по мере надобности. Он
берёт из него только те объектные файлы, которые содержат нужные
символы. Поэтому `app-static` не содержит весь zlib, а только те
функции, которые реально вызываются.

Важна последовательность архивов в команде. Компоновщик идёт по
списку слева направо и для каждого архива запоминает, какие символы
уже определены, а какие ещё нужны. Если архив стоит раньше объекта,
который его использует, нужный член может быть не извлечён. В нашем
случае объекты идут первыми, архивы — после них:

```bash
gcc -o app-static main.o funcs.o libfreetype.a libpng.a libz.a -lm
```

FreeType использует zlib, поэтому `libz.a` стоит после
`libfreetype.a` и `libpng.a`. Если поменять порядок, линковка может
упасть с `undefined reference to inflate`.

### Разделяемая библиотека

`.so` — отдельный файл, который загружается в память при запуске
программы или по `dlopen`.

У неё есть:

- **SONAME** — внутреннее имя, например `libz.so.1`;
- **DT_NEEDED** — список библиотек, которые нужны ей самой;
- **таблица динамических символов** — что она экспортирует.

Программа, слинкованная с `.so`, не содержит её код. В ELF
программы появляется запись `DT_NEEDED` с именем библиотеки, а
адреса функций подставляет динамический загрузчик при запуске.

### PIC и PIE

- **PIC** (position-independent code) — код, который может работать
  по любому адресу. Его собирают с `-fPIC` для `.so`.
- **PIE** (position-independent executable) — исполняемый файл,
  который тоже можно загрузить по произвольному адресу. Его собирают
  с `-fPIE` и линкуют с `-pie`.

Современные дистрибутивы по умолчанию собирают исполняемые файлы как
PIE. Поэтому даже `app-static` имеет тип `DYN`, а не `EXEC`.

PIC/PIE важен для blob: загрузчик отображает файл по случайному
адресу, и весь код должен использовать относительную адресацию.

### Формат ELF

У ELF-файла есть:

```text
ELF header
  e_ident     — магия 7F 45 4C 46
  e_type      — ET_EXEC, ET_DYN
  e_machine   — x86-64
  e_entry     — виртуальный адрес точки входа
  e_phoff     — где лежит таблица программных заголовков
  e_phnum     — сколько там записей

Program headers (PT_LOAD, PT_DYNAMIC, ...)
  p_type      — тип сегмента
  p_offset    — смещение в файле
  p_vaddr     — виртуальный адрес
  p_filesz    — сколько байт читать из файла
  p_memsz     — сколько байт занять в памяти
  p_flags     — R, W, X
  p_align     — выравнивание
```

Для загрузки нужны сегменты `PT_LOAD`. Сегмент `PT_DYNAMIC` хранит
динамическую информацию: таблицу релокаций, SONAME, `DT_NEEDED`.
Поле `e_entry` задаёт адрес, с которого начнётся выполнение.

### Релокации

PIE-файл не знает, по какому адресу его загрузят. Поэтому все
абсолютные адреса в нём записаны как «смещение от базы» и требуют
правки при загрузке. Эта правка называется релокацией.

В x86-64 чаще всего встречается:

```text
R_X86_64_RELATIVE
```

Она означает:

```text
по адресу (база + r_offset) записать (база + r_addend)
```

В нашем blob таких релокаций 1311. Других типов нет, потому что все
внешние символы разрешены на этапе компоновки внутри самого blob.

### libc и таблица функций

Обычная программа на C получает `malloc`, `printf`, `fopen` и другие
функции из libc. Динамический загрузчик подключает libc автоматически.

Blob собран с `-nostdlib`, поэтому своей libc у него нет. Но внутри blob
лежат статические `libz.a`, `libpng.a` и `libfreetype.a`, и они всё
равно вызывают `malloc`, `memcpy`, `fopen`, `open`, `mmap` и т. д.

Решение: загрузчик передаёт blob таблицу указателей на настоящие
функции libc. Внутри blob остаются маленькие обёртки с теми же
именами (`malloc`, `memcpy`, ...), которые просто прыгают по
указателю из таблицы. Для компоновщика это обычные определённые
символы, поэтому `--no-undefined` проходит.

### Формат 26.6

FreeType хранит размеры в формате с фиксированной точкой 26.6:

```text
значение = целая часть × 64 + дробная часть
```

Одна единица равна `1/64` пикселя. Чтобы получить пиксели, нужно
сдвинуть число вправо на 6:

```c
int pixels = (int)(value >> 6);
```

Так сделано для `advance.x`, `ascender` и `descender`. Размеры
битмапа (`bitmap.width`, `bitmap.rows`, `bitmap_left`, `bitmap_top`)
уже целые пиксели.

## 4. Общая схема

### Три способа получить один и тот же код

```text
                    app/funcs.c
                         │
        ┌────────────────┼────────────────┐
        │                │                │
   MODE_STATIC      MODE_DYNAMIC      MODE_BLOB
        │                │                │
        ▼                ▼                ▼
  libfreetype.a     dlopen(...)      -nostdlib
  libpng.a          dlsym(...)       host_shim.c
  libz.a            вызовы через     таблица libc
        │            указатели            │
        ▼                ▼                ▼
  app-static       app-dynamic       app-blob
                                         │
                                         ▼
                                    elfloader
```

`funcs.c` во всех трёх случаях один и тот же. Разница спрятана в
заголовках и флагах компилятора:

- `MODE_DYNAMIC` подключает `dynload.h`, где имена функций
  заменяются на указатели;
- `MODE_BLOB` меняет точку входа и подключает `host_api.h`;
- `MODE_STATIC` не делает ничего особенного.

### Что происходит при запуске

```text
app-static:
  ядро + динамический загрузчик
    → загружают libc/libm
    → передают управление _start
    → libc вызывает main
    → main меряет время и рисует PNG

app-dynamic:
  ядро + динамический загрузчик
    → загружают libc
    → main
    → load_libraries: dlopen libz, libpng, libfreetype
    → dlsym: заполнение указателей
    → render_png
    → unload_libraries

app-blob:
  elfloader (обычная программа)
    → open + read ELF-заголовка
    → mmap анонимной памяти
    → копирование PT_LOAD
    → релокации
    → заполнение host_api
    → вызов blob_entry
    → blob рисует PNG через таблицу libc
    → возврат в elfloader
    → munmap
```

Важно, что blob — не отдельный процесс. Он выполняется в адресном
пространстве `elfloader`, на его стеке, и вызывает его libc через
указатели. Поэтому передача `struct blob_params` — это обычная
передача указателя на стеке загрузчика.

## 5. main.c: три входа в одну программу

Файл:

- [`app/main.c`](../app/main.c)

### Выбор режима

В начале файла:

```c
#include "funcs.h"

#include <stdio.h>
#include <time.h>

#ifdef MODE_DYNAMIC
#include "dynload.h"
#endif
#ifdef MODE_BLOB
#include "host_api.h"
#endif
```

Компилятор получает один из флагов:

```bash
gcc -DMODE_STATIC  ...
gcc -DMODE_DYNAMIC ...
gcc -DMODE_BLOB    ...
```

От этого зависит, какая ветка кода попадёт в объектный файл.

### Измерение времени

```c
static double seconds_between(const struct timespec *a, const struct timespec *b)
{
    return (double)(b->tv_sec - a->tv_sec) +
           (double)(b->tv_nsec - a->tv_nsec) / 1000000000.0;
}
```

Считается разница секунд плюс разница наносекунд. Формула работает и
когда `b` и `a` находятся в разных секундах: например,

```text
a = 1.900000000
b = 2.100000000

(b.sec - a.sec) = 1
(b.nsec - a.nsec) = -800000000
1 + (-0.8) = 0.2
```

`CLOCK_MONOTONIC` выбран потому, что он не прыгает при смене
системного времени. Для измерения интервалов это правильные часы.

```c
static void print_span(const char *label, const struct timespec *from,
                       const struct timespec *to)
{
    printf("%s: %.6f s\n", label, seconds_between(from, to));
}
```

### `main` для static и dynamic

```c
int main(int argc, char **argv)
{
    struct timespec start;
    struct timespec loaded;
    struct timespec now;
    const char *program = (argc > 0 && argv[0]) ? argv[0] : "app";

    clock_gettime(CLOCK_MONOTONIC, &start);
    if (argc != 4) {
        printf("usage: %s font png text\n", program);
        print_span("load", &start, &start);
        print_span("total", &start, &start);
        return 0;
    }

#ifdef MODE_DYNAMIC
    if (!load_libraries()) {
        clock_gettime(CLOCK_MONOTONIC, &now);
        print_span("load", &start, &now);
        print_span("total", &start, &now);
        return 0;
    }
#endif

    clock_gettime(CLOCK_MONOTONIC, &loaded);
    print_span("load", &start, &loaded);
    render_png(argv[1], argv[2], argv[3]);
    clock_gettime(CLOCK_MONOTONIC, &now);
    print_span("total", &start, &now);

#ifdef MODE_DYNAMIC
    unload_libraries();
#endif
    return 0;
}
```

Порядок:

1. Запомнить время входа в `main`.
2. Проверить аргументы.
3. В dynamic-сборке загрузить библиотеки.
4. Запомнить время после загрузки и напечатать `load`.
5. Нарисовать PNG.
6. Напечатать `total`.
7. В dynamic-сборке выгрузить библиотеки.

Для static `load` равен нулю, потому что код библиотек уже находится в
образе программы. Динамический загрузчик сделал свою работу до
входа в `main`, и в измеряемый интервал она не попадает.

Для dynamic в `load` входят `dlopen` и все вызовы `dlsym`.

### Почему при ошибке возвращается 0

По заданию программа не должна завершаться аварийно ни при каких
аргументах. Поэтому:

- неверное число аргументов — печать `usage` и `return 0`;
- не загрузилась библиотека — печать ошибки и `return 0`;
- не открылся шрифт — `render_png` печатает сообщение и возвращает
  `-1`, но `main` это значение игнорирует и всё равно возвращает 0.

Это осознанное решение для лабораторной, а не ошибка.

### `blob_entry`

```c
int blob_entry(struct blob_params *params)
{
    struct timespec start;
    struct timespec loaded;
    struct timespec now;

    if (!params || !params->font_path || !params->png_path || !params->text ||
        !params->api.vprintf)
        return 0;

    host_install(&params->api);
    clock_gettime(CLOCK_MONOTONIC, &start);
    /* Библиотеки уже внутри файла. Отдельной загрузки в blob_entry нет. */
    loaded = start;
    print_span("load", &start, &loaded);
    render_png(params->font_path, params->png_path, params->text);
    clock_gettime(CLOCK_MONOTONIC, &now);
    print_span("total", &start, &now);
    return 0;
}
```

Отличия от `main`:

- нет `argc`/`argv` — параметры приходят структурой;
- сначала проверяется, что загрузчик передал всё нужное;
- `host_install` устанавливает таблицу libc **до** первого вызова
  `clock_gettime`, потому что `clock_gettime` в blob — это обёртка,
  которой нужна таблица;
- `load` всегда ноль: библиотеки уже внутри файла, отдельного
  `dlopen` нет. Реальная работа загрузчика (mmap, копирование
  сегментов, релокации) происходит до вызова `blob_entry` и в это
  время не входит;
- точка входа называется не `main`, а `blob_entry`, и её адрес
  задаётся компоновщику флагом `-Wl,-e,blob_entry`.

## 6. funcs.c: как рисуется PNG

Файл:

- [`app/funcs.c`](../app/funcs.c)

Заголовок:

- [`app/funcs.h`](../app/funcs.h)

В заголовке только одна функция:

```c
int render_png(const char *font_path, const char *png_path, const char *text);
```

Возврат:

- `0` — PNG записан;
- `-1` — ошибка уже напечатана, программа не падает.

### Константы

```c
#define FONT_PX 48
#define PAD 8
#define TEXT_LIMIT 200
```

- `FONT_PX` — размер шрифта в пикселях;
- `PAD` — поля вокруг текста;
- `TEXT_LIMIT` — максимум символов, чтобы случайно не выделить
  гигантский буфер.

### Общий конвейер `render_png`

```c
int render_png(const char *font_path, const char *png_path, const char *text)
{
    FT_Library library = NULL;
    FT_Face face = NULL;
    unsigned char *image = NULL;
    int failed = 0;
    int count = 0;
    int width = PAD;
    int ascent;
    int descent;
    int height;
    int baseline;
    int pen_x = PAD;

    if (!font_path || !png_path || !text) {
        printf("render_png: missing argument\n");
        return -1;
    }

    printf("zlib %s\n", zlibVersion());

    if (FT_Init_FreeType(&library) != 0) {
        printf("FT_Init_FreeType failed\n");
        return -1;
    }
    if (FT_New_Face(library, font_path, 0, &face) != 0) {
        printf("cannot open font '%s'\n", font_path);
        failed = 1;
        goto done;
    }
    if (FT_Set_Pixel_Sizes(face, 0, FONT_PX) != 0) {
        printf("FT_Set_Pixel_Sizes failed\n");
        failed = 1;
        goto done;
    }
    ...
```

Шаги:

1. Проверить, что все три аргумента не `NULL`.
2. Напечатать версию zlib. Это единственное место, где zlib
   вызывается явно, а не только внутри libpng. Так видно, что
   библиотека действительно подключена.
3. Инициализировать FreeType: `FT_Init_FreeType` создаёт объект
   `FT_Library`.
4. Загрузить шрифт: `FT_New_Face(library, path, 0, &face)`.
   Третий аргумент `0` — индекс лица в файле; в обычном TTF оно
   одно.
5. Установить размер: `FT_Set_Pixel_Sizes(face, 0, 48)`. Ноль в
   ширине означает «подобрать по высоте».

### Подсчёт длины текста

```c
while (text[count] != '\0' && count < TEXT_LIMIT)
    count++;
```

Считаются **байты**, а не Unicode-символы. Для `TRSPO` это одно и то
же. Для кириллицы в UTF-8 один символ занимает два байта, и такой
код нарисует два глифа вместо одного. Это ограничение отмечено в
конце документа.

### Метрики шрифта

```c
/* 26.6: единица FreeType — 1/64 пикселя, поэтому сдвиг на 6. */
ascent = (int)(face->size->metrics.ascender >> 6);
descent = (int)(-(face->size->metrics.descender >> 6));
if (ascent < 1)
    ascent = FONT_PX;
if (descent < 0)
    descent = 0;
height = ascent + descent + PAD * 2;
baseline = PAD + ascent;
```

- `ascender` — насколько символы поднимаются выше базовой линии;
- `descender` — насколько опускаются ниже (в FreeType это
  отрицательное число, поэтому берётся минус);
- `baseline` — вертикальная координата базовой линии;
- `height` — высота картинки.

Если шрифт вернул странные метрики, код подставляет `FONT_PX` и ноль,
чтобы не получить отрицательную или нулевую высоту.

### Первый проход: вычисление ширины

```c
for (int i = 0; i < count; i++) {
    FT_UInt index = FT_Get_Char_Index(face, (unsigned char)text[i]);
    if (index == 0 || FT_Load_Glyph(face, index, FT_LOAD_DEFAULT) != 0) {
        width += FONT_PX / 2;
        continue;
    }
    width += (int)(face->glyph->advance.x >> 6);
}
width += PAD;
```

Почему два прохода? Ширина картинки должна быть известна до
`malloc`, а горизонтальное продвижение каждого глифа становится
известно только после `FT_Load_Glyph`. Поэтому сначала текст
«измеряется», потом выделяется память и рисуется.

`FT_Get_Char_Index` переводит код символа в индекс глифа в шрифте.
Если символа нет (`index == 0`) или глиф не загрузился, добавляется
половина `FONT_PX`, чтобы текст не слипался.

`advance.x` — это 26.6, поэтому `>> 6`.

### Выделение буфера

```c
image = malloc((size_t)height * (size_t)width * 3);
if (!image) {
    printf("out of memory\n");
    failed = 1;
    goto done;
}
memset(image, 0xFF, (size_t)height * (size_t)width * 3);
```

Буфер — RGB, три байта на пиксель. `0xFF` во всех байтах означает
белый цвет. Размер перемножается в `size_t`, чтобы на больших
картинках не переполнить `int`.

### Второй проход: рисование

```c
for (int i = 0; i < count; i++) {
    FT_UInt index = FT_Get_Char_Index(face, (unsigned char)text[i]);
    int advance = FONT_PX / 2;
    if (index != 0 && FT_Load_Glyph(face, index, FT_LOAD_RENDER) == 0) {
        paint_glyph(image, width, height, pen_x, baseline, face->glyph);
        advance = (int)(face->glyph->advance.x >> 6);
        if (advance <= 0)
            advance = FONT_PX / 2;
    }
    pen_x += advance;
}
```

Здесь `FT_LOAD_RENDER` уже не только загружает глиф, но и
растеризует его в битмап. `paint_glyph` переносит битмап в общий
буфер, после чего `pen_x` сдвигается на ширину глифа.

### `paint_glyph`

```c
static void paint_glyph(unsigned char *image, int width, int height,
                        int pen_x, int baseline, FT_GlyphSlot glyph)
{
    FT_Bitmap *bitmap = &glyph->bitmap;
    int pitch;

    if (bitmap->pixel_mode != FT_PIXEL_MODE_GRAY || !bitmap->buffer)
        return;

    pitch = bitmap->pitch < 0 ? -bitmap->pitch : bitmap->pitch;
    for (unsigned int row = 0; row < bitmap->rows; row++) {
        int y = baseline - glyph->bitmap_top + (int)row;
        if (y < 0 || y >= height)
            continue;
        for (unsigned int col = 0; col < bitmap->width; col++) {
            int x = pen_x + glyph->bitmap_left + (int)col;
            unsigned char *pixel;
            unsigned char coverage;
            if (x < 0 || x >= width)
                continue;
            coverage = bitmap->buffer[row * (unsigned int)pitch + col];
            pixel = image + ((size_t)y * (size_t)width + (size_t)x) * 3;
            pixel[0] = pixel[1] = pixel[2] = (unsigned char)(255 - coverage);
        }
    }
}
```

Что важно:

- `FT_PIXEL_MODE_GRAY` — 8-битное покрытие, по одному байту на
  пиксель. Другие режимы (монохром, LCD) здесь не поддерживаются.
- `pitch` — количество байт в строке битмапа. Оно может быть
  отрицательным, если битмап перевёрнут; поэтому берётся модуль.
- `bitmap_left` и `bitmap_top` задают положение битмапа относительно
  точки `pen_x`/`baseline`.
- `coverage` — 0 для пустого пикселя, 255 для полностью покрытого.
- `255 - coverage` даёт белый фон и тёмный текст: при покрытии 255
  пиксель становится чёрным, при 0 остаётся белым.

Это простой способ сгладить текст без альфа-канала. Минус: если
глифы перекрываются, следующий глиф перезаписывает предыдущий, а не
смешивается с ним. Для обычного текста с нормальными advance этого
не происходит.

### Запись PNG

```c
static int write_png(const char *path, unsigned char *image, int width, int height)
{
    FILE *fp;
    png_structp png_ptr;
    png_infop info;
    /* longjmp откатывает регистры. Без volatile указатель rows после ошибки был бы потерян. */
    png_bytep * volatile rows = NULL;

    fp = fopen(path, "wb");
    if (!fp) {
        printf("cannot create png '%s'\n", path);
        return -1;
    }

    png_ptr = png_create_write_struct(PNG_LIBPNG_VER_STRING, NULL, NULL, NULL);
    ...
    info = png_create_info_struct(png_ptr);
    ...
    if (setjmp(*png_set_longjmp_fn(png_ptr, longjmp, sizeof(jmp_buf)))) {
        printf("png write failed for '%s'\n", path);
        free(rows);
        png_destroy_write_struct(&png_ptr, &info);
        fclose(fp);
        return -1;
    }

    png_init_io(png_ptr, fp);
    png_set_IHDR(png_ptr, info, (png_uint_32)width, (png_uint_32)height, 8,
                 PNG_COLOR_TYPE_RGB, PNG_INTERLACE_NONE,
                 PNG_COMPRESSION_TYPE_DEFAULT, PNG_FILTER_TYPE_DEFAULT);

    rows = malloc((size_t)height * sizeof(png_bytep));
    ...
    for (int y = 0; y < height; y++)
        rows[y] = image + (size_t)y * (size_t)width * 3;

    png_write_info(png_ptr, info);
    png_write_image(png_ptr, rows);
    png_write_end(png_ptr, info);

    free(rows);
    rows = NULL;
    png_destroy_write_struct(&png_ptr, &info);
    if (fclose(fp) != 0) {
        printf("cannot close png '%s'\n", path);
        return -1;
    }
    return 0;
}
```

Разбор:

1. `fopen(..., "wb")` — бинарная запись.
2. `png_create_write_struct` создаёт основной объект libpng.
3. `png_create_info_struct` создаёт объект с параметрами изображения.
4. `png_set_longjmp_fn` возвращает указатель на `jmp_buf`, который
   libpng будет использовать для ошибок. `setjmp` запоминает точку
   возврата. Если libpng обнаружит ошибку, она вызовет `longjmp`, и
   управление вернётся сюда с ненулевым значением. Тогда код
   освобождает память и структуры.
5. `png_init_io` связывает libpng с `FILE *`.
6. `png_set_IHDR` задаёт:
   - ширину и высоту;
   - 8 бит на канал;
   - `PNG_COLOR_TYPE_RGB` — без альфа-канала;
   - без интерлейсинга;
   - стандартное сжатие и фильтрацию.
7. `rows` — массив указателей на строки. libpng принимает именно
   массив, а не сплошной буфер.
8. `png_write_info`, `png_write_image`, `png_write_end` пишут файл.
9. Освобождение: `free(rows)`, `png_destroy_write_struct`,
   `fclose`.

### Почему `rows` объявлен `volatile`

Стандарт C говорит: если переменная изменена после `setjmp` и имеет
автоматическое хранение, после `longjmp` её значение не определено,
кроме случая, когда она объявлена `volatile`. `rows` присваивается
после `setjmp`, а читается в обработчике ошибки. Без `volatile`
компилятор мог бы держать значение в регистре, который `longjmp`
восстанавливает к старому состоянию, и `free(rows)` получил бы мусор.
С `volatile` значение всегда читается из памяти.

### Где здесь zlib

Явно zlib вызывается один раз:

```c
printf("zlib %s\n", zlibVersion());
```

Неявно libpng использует zlib при записи `IDAT`: сжатие пиксельных
данных по DEFLATE. Поэтому в статической сборке в бинарник попадает
и `libz.a`, а в динамической `libz.so.1` загружается первой.

### Итоговый размер

Для `TRSPO` и `font.ttf` получается PNG 202×106:

```text
ширина  = 8 (PAD) + сумма advance + 8 (PAD) = 202
высота  = ascent + descent + 2 * 8 = 106
```

Размер файла — 5669 байт, число не белых пикселей — 3834.

## 7. Статическая сборка

Цель:

```bash
make static
```

Команда компоновки:

```bash
gcc -o build/app-static \
    app/object_files/static/main.o \
    app/object_files/funcs.o \
    build/libfreetype.a build/libpng.a build/libz.a -lm
```

### Что делает компоновщик

1. Начинает с `main.o` и `funcs.o`. В них есть ссылки на `FT_*`,
   `png_*` и `zlibVersion`.
2. Видит `libfreetype.a`, ищет в архиве объектные файлы, которые
   определяют нужные `FT_*`. Достаёт их.
3. Эти объектные файлы ссылаются на `inflate`, `malloc`, `memcpy` и
   другие функции. `malloc`/`memcpy` будут разрешены позже из libc,
   а `inflate` — из `libz.a`.
4. Видит `libpng.a`, достаёт нужные `png_*`.
5. Видит `libz.a`, достаёт `inflate`, `deflate`, `crc32` и т. д.
6. `-lm` подключает математическую библиотеку.

В итоговый файл попадают только нужные объектные файлы. Это называют
«вытягиванием» членов архива.

### Проверка зависимостей

```bash
ldd build/app-static
```

```text
linux-vdso.so.1
libm.so.6
libc.so.6
/lib64/ld-linux-x86-64.so.2
```

Трёх библиотек в списке нет. Это и есть признак статической
компоновки именно их.

При этом libc и libm остаются динамическими. Задание требует
статически слинковать три конкретные библиотеки, а не сделать
полностью статический бинарник. Полная статическая сборка с glibc
сложнее и здесь не нужна.

`file build/app-static` показывает:

```text
ELF 64-bit LSB pie executable, x86-64, dynamically linked, ...
```

Слово `pie` здесь нормально: современный gcc по умолчанию собирает
PIE. Статическими являются три библиотеки, а не весь процесс
загрузки.

## 8. Динамическая сборка

Цель:

```bash
make dynamic
```

Команда компоновки:

```bash
gcc -o build/app-dynamic \
    app/object_files/dynamic/main.o \
    app/object_files/dynamic/funcs.o \
    app/object_files/dynamic/dynload.o -ldl
```

Три библиотеки в команде не указаны. В ELF программы нет
`DT_NEEDED` для них. Есть только libc (в современных glibc `libdl`
объединена с libc, поэтому `-ldl` может не добавлять отдельную
зависимость).

### `open_beside`

Файл:

- [`app/dynload.c`](../app/dynload.c)

```c
static void *open_beside(const char *filename)
{
    char exe[PATH_MAX];
    char path[PATH_MAX];
    ssize_t length;
    char *slash;
    void *handle;

    length = readlink("/proc/self/exe", exe, sizeof exe - 1);
    if (length < 0) {
        printf("cannot read /proc/self/exe\n");
        return NULL;
    }
    exe[length] = '\0';
    slash = strrchr(exe, '/');
    if (!slash) {
        printf("cannot resolve path to %s\n", filename);
        return NULL;
    }
    *slash = '\0';
    if (snprintf(path, sizeof path, "%s/%s", exe, filename) >= (int)sizeof path) {
        printf("path to %s is too long\n", filename);
        return NULL;
    }

    handle = dlopen(path, RTLD_NOW | RTLD_GLOBAL);
    if (!handle)
        printf("dlopen %s: %s\n", path, dlerror());
    return handle;
}
```

`/proc/self/exe` — символическая ссылка на исполняемый файл текущего
процесса. `readlink` возвращает его путь. Затем путь обрезается до
каталога и к нему добавляется имя `.so`.

Почему так, а не просто `dlopen("libz.so.1", ...)`? При запуске не
из каталога `lab2` динамический загрузчик искал бы библиотеку в
системных путях, а не рядом с программой. `open_beside` делает
результат независимым от текущего каталога.

`snprintf` возвращает длину, которая была бы записана. Если она
больше или равна размеру буфера, путь обрезан — это проверяется.

### Флаги `dlopen`

```c
RTLD_NOW | RTLD_GLOBAL
```

- `RTLD_NOW` — разрешить все символы библиотеки сразу при загрузке.
  Если чего-то не хватает, ошибка будет здесь, а не при первом
  вызове функции.
- `RTLD_GLOBAL` — сделать символы библиотеки видимыми для других
  объектов, загружаемых позже. Это удобно для цепочки
  zlib → libpng → freetype.

### Порядок загрузки

```c
libz = open_beside("libz.so.1");
libpng = libz ? open_beside("libpng.so") : NULL;
freetype = libpng ? open_beside("libfreetype.so") : NULL;
```

Сначала zlib. `libpng.so` и `libfreetype.so` имеют
`DT_NEEDED: libz.so.1`. Если загрузить их первыми, динамический
загрузчик сам начнёт искать libz и может взять другую копию — из
`RUNPATH`, системного каталога или кэша. Явная загрузка локальной
`libz.so.1` первой гарантирует, что дальше будет использована именно
она: загрузчик узнаёт уже открытую библиотеку по SONAME и
переиспользует её.

Проверить зависимости можно так:

```bash
readelf -d build/libpng.so | grep NEEDED
readelf -d build/libfreetype.so | grep NEEDED
```

```text
(NEEDED) Shared library: [libz.so.1]
(NEEDED) Shared library: [libm.so.6]
(NEEDED) Shared library: [libc.so.6]

(NEEDED) Shared library: [libz.so.1]
(NEEDED) Shared library: [libc.so.6]
```

### `bind` и `dlsym`

```c
static int bind(void *lib, const char *name, void *slot)
{
    void *symbol;

    dlerror();
    symbol = dlsym(lib, name);
    if (dlerror() != NULL || symbol == NULL) {
        printf("dlsym %s failed\n", name);
        return 0;
    }
    /* dlsym отдаёт void *. В слот кладётся тот же адрес, что у функции. */
    memcpy(slot, &symbol, sizeof symbol);
    return 1;
}
```

Тонкости:

- `dlerror()` вызывается перед `dlsym`, чтобы очистить старую ошибку.
  После вызова проверяется снова: `dlsym` может вернуть `NULL` и при
  успехе, если символ действительно лежит по нулевому адресу (редко,
  но стандарт это допускает).
- `slot` — адрес переменной-указателя на функцию. `memcpy`
  копирует биты `void *` в функцию-указатель. Прямое присваивание
  `*(void **)slot = symbol` было бы нарушением строгого алиасинга, а
  преобразование `void *` в указатель на функцию не гарантируется
  стандартом C. На x86-64 оба указателя одного размера, поэтому
  копирование байтов работает.

```c
FT_New_Face(library, font_path, 0, &face)
```

После препроцессирования в dynamic-сборке получается:

```c
p_FT_New_Face(library, font_path, 0, &face)
```

То есть вызов функции через указатель. Код рисования при этом
остаётся одинаковым для static и dynamic.

Заголовок `dynload.h` подключается **после** заголовков FreeType,
libpng и zlib. Иначе макросы испортили бы объявления самих функций.
В `funcs.c` порядок такой:

```c
#include <ft2build.h>
#include FT_FREETYPE_H
#include <png.h>
#include <setjmp.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <zlib.h>

#ifdef MODE_DYNAMIC
#include "dynload.h"
#endif
```

### Почему `funcs.c` для dynamic отдельный объект

В `app/Makefile`:

```make
$(OBJDIR)/funcs.o: funcs.c funcs.h
	gcc $(HOST_CFLAGS) -c funcs.c -o $@

$(OBJDIR)/dynamic/funcs.o: funcs.c funcs.h dynload.h
	gcc $(HOST_CFLAGS) -DMODE_DYNAMIC -c funcs.c -o $@
```

Один и тот же `funcs.c` компилируется дважды с разными флагами.
Static-версия не включает `dynload.h`, dynamic-версия включает.

### Выгрузка

```c
void unload_libraries(void)
{
    if (freetype)
        dlclose(freetype);
    if (libpng)
        dlclose(libpng);
    if (libz)
        dlclose(libz);
    freetype = NULL;
    libpng = NULL;
    libz = NULL;
}
```

Порядок обратный загрузке: сначала FreeType (зависит от libpng и
zlib), потом libpng (зависит от zlib), потом zlib. `dlclose`
уменьшает счётчик ссылок; если библиотеку никто больше не держит,
она выгружается.

После `dlclose` указатели на функции становятся недействительными,
поэтому `unload_libraries` вызывается только после `render_png` и
печати `total`.

### Время

В `load` входят:

- `readlink`;
- три `dlopen`;
- семнадцать `dlsym`;
- проверки ошибок.

На прогретом кеше это доли миллисекунды. Первый запуск после сборки
может быть медленнее из-за чтения файлов с диска.

## 9. Blob-сборка

Цель:

```bash
make blob
```

Результат:

```text
build/app-blob
build/elfloader
```

Blob — это ELF-файл, который не является обычной программой:

- нет `main`;
- нет `_start`;
- нет собственной libc;
- нет `PT_INTERP`;
- нет `DT_NEEDED`;
- точка входа — `blob_entry`.

Его нельзя нормально запустить командой `./build/app-blob`. Ядро
технически может загрузить static PIE без интерпретатора, но
`blob_entry` ожидает указатель на `struct blob_params`, а при обычном
запуске получит совсем другие аргументы. Поэтому blob загружает
отдельная программа `elfloader`.

### Команда компоновки

```bash
gcc -nostdlib -pie -fPIE \
    -Wl,-e,blob_entry -Wl,--no-dynamic-linker -Wl,--no-undefined \
    -Wl,-Bsymbolic -Wl,--version-script,blob.map \
    -o build/app-blob \
    app/object_files/blob/main.o \
    app/object_files/blob/funcs.o \
    app/object_files/blob/host_shim.o \
    app/object_files/blob/setjmp_stub.o \
    build/libfreetype.a build/libpng.a build/libz.a -lgcc
```

Разберём каждый флаг.

#### `-nostdlib`

Не подключать:

- стартовые файлы (`crt1.o`, `crti.o`, `crtbegin.o`);
- стандартные библиотеки (`libc`, `libgcc` и т. д.).

Поэтому нет `_start`, который обычно вызывает `__libc_start_main`, а
тот — `main`. Точку входа приходится задавать вручную.

#### `-pie -fPIE`

Собрать позиционно-независимый исполняемый файл. Код использует
относительную адресацию, а абсолютные адреса оформляются как
релокации. Загрузчик может отобразить файл по любому адресу.

Статические библиотеки тоже собраны с `-fPIC`, иначе их код нельзя
было бы положить в PIE по произвольному адресу.

#### `-Wl,-e,blob_entry`

Задать точку входа. В ELF-заголовке появляется:

```text
Entry point address: 0x8040
```

Это виртуальный адрес `blob_entry` внутри файла.

#### `-Wl,--no-dynamic-linker`

Не добавлять `PT_INTERP`. Обычный динамически слинкованный PIE
требует интерпретатор, который загрузит libc и выполнит релокации.
Нам это не нужно: релокации применяет `elfloader`.

#### `-Wl,--no-undefined`

Требовать, чтобы все символы были разрешены на этапе компоновки.
Если какая-то функция libc забыта в `host_shim.c`, сборка упадёт
сразу. Без этого флага в blob могли бы остаться динамические
импорты, и загрузчик получил бы `GLOB_DAT`/`JUMP_SLOT`, которые он не
умеет применять.

#### `-Wl,-Bsymbolic`

Связать внутренние обращения с определениями внутри blob. Это
гарантирует, что `malloc` из libpng вызовет нашу обёртку, а не
одноимённый символ из глобальной области видимости загрузчика.

#### `-Wl,--version-script,blob.map`

Файл [`app/blob.map`](../app/blob.map):

```text
{
  local: *;
};
```

Все символы делаются локальными. В динамической таблице символов
остаётся только нулевая запись:

```bash
readelf --dyn-syms build/app-blob
```

```text
Symbol table '.dynsym' contains 1 entry:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND
```

Наружу blob ничего не экспортирует. При этом статическая таблица
символов `.symtab` сохраняется (файл не stripped), и в ней видно
`blob_entry` как локальный символ.

#### `-lgcc`

Компилятор может вставлять вызовы своих служебных функций, например
для деления 128-битных чисел или работы с длинными целыми. Это не
libc, а runtime самой GCC. `-nostdlib` отключает автоматическое
подключение, поэтому `-lgcc` указан явно.

### Флаги компиляции blob

В `app/Makefile`:

```make
HOST_CFLAGS := -Wall -Wextra -O2 -fPIC -fno-stack-protector \
	-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0 -MMD -MP $(INCLUDES)
BLOB_CFLAGS := $(HOST_CFLAGS) -fPIE -fno-builtin \
	-fno-asynchronous-unwind-tables
```

- `-fno-stack-protector` — не добавлять проверку канарейки стека.
  Она вызывает `__stack_chk_fail` из libc, которой в blob нет.
- `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0` — отключить fortify.
  Иначе компилятор заменит `memcpy` на `__memcpy_chk`, а такой
  функции в таблице нет.
- `-fPIE` — позиционно-независимый код для исполняемого файла.
- `-fno-builtin` — не превращать циклы и вызовы в встроенные
  реализации, чтобы не появились неожиданные обращения к libc.
- `-fno-asynchronous-unwind-tables` — не генерировать `.eh_frame`.
  Разворачивать исключения в blob всё равно некому; таблицы только
  увеличивают файл.

Те же флаги применяются к `main.c`, `funcs.c` и `host_shim.c`.
`setjmp_stub.S` ассемблируется отдельно, без этих флагов — там уже
написан нужный код.

### Таблица функций libc

Файл:

- [`app/host_api.h`](../app/host_api.h)

```c
struct host_api {
    FILE *(*fopen)(const char *path, const char *mode);
    int (*fclose)(FILE *stream);
    size_t (*fread)(void *ptr, size_t size, size_t nmemb, FILE *stream);
    size_t (*fwrite)(const void *ptr, size_t size, size_t nmemb, FILE *stream);
    int (*fseek)(FILE *stream, long offset, int whence);
    long (*ftell)(FILE *stream);
    int (*fflush)(FILE *stream);
    int (*ferror)(FILE *stream);
    int (*fputc)(int c, FILE *stream);
    int (*remove)(const char *pathname);

    void *(*malloc)(size_t size);
    void *(*calloc)(size_t nmemb, size_t size);
    void *(*realloc)(void *ptr, size_t size);
    void (*free)(void *ptr);

    void *(*memcpy)(void *dest, const void *src, size_t n);
    ...
};
```

Это обычная структура с указателями на функции. Она описана
одинаково в blob и в загрузчике, потому что оба включают
`host_api.h`. Важно, чтобы порядок полей и типы совпадали: загрузчик
и blob — разные единицы трансляции, но структура передаётся по
указателю, и blob читает её по своему описанию. Оба файла
компилируются на одной машине с одними заголовками, поэтому
согласованность сохраняется.

Категории функций:

| Категория | Зачем |
|---|---|
| `fopen`, `fread`, `fwrite`, `fseek`, `ftell` | libpng и FreeType читают/пишут файлы |
| `malloc`, `calloc`, `realloc`, `free` | выделение памяти внутри библиотек |
| `memcpy`, `memset`, `memcmp`, `strlen`, `strcpy` | строки и память |
| `vprintf`, `vsprintf`, `vfprintf`, `vsnprintf` | печать |
| `qsort` | используется внутри FreeType |
| `pow`, `frexp`, `modf`, `floor`, `fabs` | математика |
| `clock_gettime`, `gmtime` | время |
| `setjmp_fn`, `longjmp_fn` | обработка ошибок libpng |
| `errno_location` | доступ к `errno` |
| `open_fn`, `close_fn`, `read_fn`, `fcntl_fn`, `fstat_fn`, `mmap_fn`, `munmap_fn` | POSIX-вызовы, если они понадобятся библиотеке |
| `stderr_file`, `stdout_file` | стандартные потоки |
| `abort_fn` | аварийное завершение |

Почему есть и `fopen`, и `open`? libpng и текущий FreeType работают
через `FILE *` и `fopen`: системный слой — `src/base/ftsystem.c`.
`open` и `mmap` в таблице остаются, blob их отдаёт, но эта сборка
FreeType ими не пользуется.

### `struct blob_params`

```c
struct blob_params {
    const char *font_path;
    const char *png_path;
    const char *text;
    struct host_api api;
};
```

Загрузчик заполняет эту структуру и передаёт её указателем в
`blob_entry`. Строки — это `argv` загрузчика; они живут в его
адресном пространстве и остаются валидными на время вызова.

### Обёртки `host_shim.c`

Файл:

- [`app/host_shim.c`](../app/host_shim.c)

В начале:

```c
static const struct host_api *api;

void host_install(const struct host_api *src)
{
    api = src;
    host_setjmp_fn = src ? src->setjmp_fn : NULL;
    host_longjmp_fn = src ? src->longjmp_fn : NULL;
    if (src) {
        stderr = src->stderr_file;
        stdout = src->stdout_file;
    }
}
```

`api` — глобальный указатель в `.bss` blob. До `host_install` он
нулевой. `blob_entry` вызывает `host_install` первым делом, поэтому
дальше все обёртки работают.

Каждая обёртка устроена однотипно:

```c
void *malloc(size_t size)
{
    return (api && api->malloc) ? api->malloc(size) : NULL;
}

int fclose(FILE *stream)
{
    return (api && api->fclose) ? api->fclose(stream) : EOF;
}
```

Если таблица ещё не установлена или поле нулевое, возвращается
безопасное значение. Это не полноценная обработка ошибок, а защита
от падения: например, `memcpy` в таком случае вернёт `dest`, не
скопировав данные. На практике все поля заполнены, а
`--no-undefined` следит, чтобы нужные обёртки вообще были в файле.

#### Вариативные функции

`printf`, `sprintf`, `fprintf`, `snprintf` не могут передать свои
`...` напрямую. Поэтому в таблице лежат функции, принимающие
`va_list`:

```c
int printf(const char *fmt, ...)
{
    va_list ap;
    int result;

    if (!api || !api->vprintf)
        return -1;
    va_start(ap, fmt);
    result = api->vprintf(fmt, ap);
    va_end(ap);
    return result;
}
```

`va_start` получает доступ к списку аргументов, `va_end`
освобождает его. Такой набор `v*`-функций есть в любой libc.

#### `stderr` и `stdout`

```c
FILE *stderr;
FILE *stdout;
```

Заголовки glibc объявляют эти переменные как `extern FILE *`. Blob
должен определить их сам, иначе компоновка с `--no-undefined`
упадёт. `host_install` записывает в них реальные потоки загрузчика.
Библиотеки, которые пишут в `stderr`, попадут в тот же терминал.

#### `errno`

```c
int *__errno_location(void)
{
    static int fallback;

    if (api && api->errno_location)
        return api->errno_location();
    return &fallback;
}
```

В glibc `errno` — это макрос:

```c
#define errno (*__errno_location())
```

Blob не может использовать TLS-переменную libc напрямую, поэтому
`__errno_location` возвращает указатель на настоящий `errno`
загрузчика. Код внутри blob видит те же значения ошибок, что и
libc-функции, которые он вызывает.

#### `abort`

```c
void abort(void)
{
    if (api && api->abort_fn)
        api->abort_fn();
    for (;;)
        ;
}
```

Если таблица есть, вызывается настоящий `abort` загрузчика. Он
поднимает `SIGABRT` в том же процессе. Если таблицы нет, программа
зависает — это лучше, чем молча продолжать после аварийной
ситуации.

#### POSIX-обёртки и `.set`

С FreeType сложнее: в glibc заголовки могут объявлять `open`,
`fcntl`, `strtol` с особыми asm-именами или макросами. Например,
современная glibc объявляет `strtol` с именем `__isoc23_strtol`.
Если просто написать `int open(...)`, компоновщик может не увидеть
символ `open`, который ищут библиотеки.

Поэтому в коде:

```c
int blob_open(const char *path, int flags, ...)
{
    return (api && api->open_fn) ? api->open_fn(path, flags, 0) : -1;
}
```

а в конце файла:

```c
__asm__(
    ".globl strtol\n\t.set strtol, blob_strtol\n\t"
    ".globl open\n\t.set open, blob_open\n\t"
    ".globl close\n\t.set close, blob_close\n\t"
    ".globl read\n\t.set read, blob_read\n\t"
    ".globl fcntl\n\t.set fcntl, blob_fcntl\n\t"
    ".globl fstat\n\t.set fstat, blob_fstat\n\t"
    ".globl mmap\n\t.set mmap, blob_mmap\n\t"
    ".globl munmap\n\t.set munmap, blob_munmap\n\t"
);
```

`.set open, blob_open` создаёт символ `open`, равный `blob_open`.
Теперь любая ссылка на `open` из `libfreetype.a` разрешается в нашу
обёртку.

`open` и `fcntl` — вариативные функции. `open` всегда передаёт
`mode = 0`: он имеет смысл только при `O_CREAT`, а FreeType открывает
файл только на чтение. `fcntl` читает один `int` из `va_list`.

`mmap` возвращает `(void *)-1` при отсутствии таблицы — это
стандартное значение `MAP_FAILED`.

#### `mem*` и `str*`

В начале файла:

```c
#undef memchr
#undef memcpy
#undef memmove
#undef memset
#undef memcmp
#undef strchr
#undef strrchr
#undef strstr
#undef strcmp
#undef strncmp
#undef strcpy
#undef strncpy
#undef strcat
#undef strlen
#undef stpcpy
```

glibc с fortify превращает некоторые из этих имён в макросы. Blob
должен экспортировать настоящие функции, поэтому макросы
отменяются, а функции определяются с обычными именами.

### `setjmp_stub.S`

Файл:

- [`app/setjmp_stub.S`](../app/setjmp_stub.S)

```asm
/* jmp, а не call: setjmp должен запомнить адрес в libpng, а не в этом стабе.
 * Иначе longjmp вернётся сюда и запись PNG сломается. */
    .text
    .globl _setjmp
    .globl setjmp
    .globl __sigsetjmp
    .type _setjmp, @function
_setjmp:
setjmp:
__sigsetjmp:
    movq host_setjmp_fn(%rip), %rax
    testq %rax, %rax
    jz 1f
    jmp *%rax
1:
    xorl %eax, %eax
    ret

    .globl longjmp
    .globl _longjmp
    .type longjmp, @function
longjmp:
_longjmp:
    movq host_longjmp_fn(%rip), %rax
    testq %rax, %rax
    jz 1f
    jmp *%rax
1:
    ud2
```

Это, пожалуй, самое тонкое место в работе.

#### Зачем вообще свой `setjmp`

libpng обрабатывает ошибки через `setjmp`/`longjmp`. В blob нет
libc, поэтому символы `setjmp` и `longjmp` должны быть
определены. Можно было бы сделать обычные C-обёртки:

```c
int setjmp(jmp_buf env) {
    return _setjmp(env);
}
```

Но тогда `_setjmp` запомнит адрес возврата **внутри обёртки**, а не в
libpng. `longjmp` вернёт управление в обёртку, и только потом она
вернётся в libpng. На бумаге это может сработать, но на практике
ломается: компилятор может оптимизировать обёртку, использовать
свой пролог, а сохранённый `rsp`/`rbp` будет указывать на кадр
обёртки. `setjmp` обязан вернуться ровно в точку вызова в libpng.

#### Решение: `jmp`, а не `call`

Инструкция `jmp *%rax` передаёт управление на `_setjmp`, не добавляя
новый адрес возврата на стек. На вершине стека уже лежит адрес
возврата из libpng — тот самый, который `_setjmp` должен сохранить.
Получается, что `_setjmp` вызывается как будто напрямую из libpng.

Схема:

```text
libpng: call setjmp
    стек: [адрес возврата в libpng]
        │
        ▼
blob: setjmp:
    movq host_setjmp_fn(%rip), %rax
    jmp *%rax
        │
        ▼
libc: _setjmp
    сохраняет rsp, rbp, callee-saved регистры и адрес возврата
    (адрес возврата — в libpng)
```

При ошибке libpng вызывает `longjmp`:

```text
libc: longjmp
    восстанавливает rsp, rbp, регистры
    прыгает по сохранённому адресу возврата
        │
        ▼
libpng: продолжение после setjmp, setjmp «возвращает» ненулевое значение
```

Так `longjmp` возвращает управление именно в `write_png`, а не в
ассемблерный стаб.

#### Почему три имени

В glibc `setjmp` может быть макросом, который раскрывается в
`_setjmp` или `__sigsetjmp`. Blob экспортирует все три имени, чтобы
любой вариант вызова попал в стаб. `_setjmp` и `setjmp` — псевдонимы
одной функции; `__sigsetjmp` тоже, хотя аргумент `savemask` при
передаче в `_setjmp` игнорируется. Для PNG это не важно: сигналы в
обработке ошибок не участвуют.

Аналогично `longjmp` и `_longjmp`.

#### Проверка на `NULL`

Если `host_install` ещё не вызван, `host_setjmp_fn` равен нулю.
Тогда `setjmp` возвращает 0, ничего не сохранив. Если после этого
вызвать `longjmp`, `host_longjmp_fn` тоже ноль, и выполняется `ud2` —
гарантированная недопустимая инструкция. Это лучше, чем прыжок по
нулевому адресу со странным поведением: падение сразу покажет, что
таблица не установлена.

### Что получается в ELF

## 10. Загрузчик ELF

Файлы:

- [`elfloader/main.c`](../elfloader/main.c)
- [`elfloader/elfload/`](../elfloader/elfload/) — библиотека
  `erincandescent/elfload`

### Что делает библиотека, а что обёртка

`elfload` умеет:

- читать ELF-заголовок;
- проверять класс, порядок байтов, архитектуру, тип;
- находить `PT_LOAD` и `PT_DYNAMIC`;
- считать размер образа;
- копировать сегменты;
- применять `R_X86_64_RELATIVE`.

Обёртка `elfloader/main.c`:

- разбирает аргументы;
- открывает файл;
- даёт библиотеке callback для чтения;
- выделяет память;
- заполняет таблицу libc;
- вызывает точку входа;
- освобождает ресурсы.

### Контекст загрузчика

```c
typedef struct el_ctx {
    bool (*pread)(struct el_ctx *ctx, void *dest, size_t nb, size_t offset);

    Elf_Addr base_load_paddr;
    Elf_Addr base_load_vaddr;

    Elf_Addr memsz;
    Elf_Addr align;

    Elf_Ehdr ehdr;

    Elf_Off  dynoff;
    Elf_Addr dynsize;
} el_ctx;
```

- `pread` — функция чтения из файла;
- `base_load_paddr` и `base_load_vaddr` — куда загружать;
- `memsz` — сколько памяти нужно;
- `align` — требуемое выравнивание;
- `ehdr` — прочитанный ELF-заголовок;
- `dynoff`, `dynsize` — положение динамической секции.

### `pread_cb`

```c
static int blob_fd = -1;

static bool pread_cb(el_ctx *ctx, void *dest, size_t nb, size_t offset)
{
    ssize_t got;

    (void)ctx;
    got = pread(blob_fd, dest, nb, (off_t)offset);
    return got == (ssize_t)nb;
}
```

`pread` читает с указанного смещения, не меняя текущую позицию в
файле. Это важно: `elfload` сначала читает заголовок, потом таблицу
программных заголовков, потом сегменты — в произвольном порядке.
`read` с последовательным смещением тут неудобен.

`blob_fd` — глобальная переменная, потому что сигнатура callback не
позволяет передать произвольный контекст. Загрузчик однопоточный,
поэтому этого достаточно.

### `alloc_cb`

```c
static void *alloc_cb(el_ctx *ctx, Elf_Addr phys, Elf_Addr virt, Elf_Addr size)
{
    (void)ctx;
    (void)phys;
    (void)size;
    return (void *)(uintptr_t)virt;
}
```

Библиотека уже получила весь кусок памяти через `mmap`. Callback
должен только вернуть адрес, по которому нужно разместить сегмент.
`virt` уже включает базу загрузки, поэтому возвращается он.

### Основной поток

```c
int main(int argc, char **argv)
{
    el_ctx ctx;
    el_status status;
    struct blob_params params;
    unsigned char *mapping;
    size_t map_size;
    int (*entry)(struct blob_params *);

    if (argc != 5) {
        printf("usage: %s blob font png text\n", argc > 0 ? argv[0] : "elfloader");
        return 0;
    }

    blob_fd = open(argv[1], O_RDONLY);
    if (blob_fd < 0) {
        printf("cannot open blob '%s': %s\n", argv[1], strerror(errno));
        return 0;
    }

    memset(&ctx, 0, sizeof ctx);
    ctx.pread = pread_cb;

    status = el_init(&ctx);
    if (status != EL_OK) {
        printf("el_init failed: %s (%d)\n", status_name(status), status);
        close(blob_fd);
        return 0;
    }

    if (ctx.memsz == 0) {
        printf("blob has no loadable segments\n");
        close(blob_fd);
        return 0;
    }

    map_size = (size_t)ctx.memsz;
    mapping = mmap(NULL, map_size, PROT_READ | PROT_WRITE | PROT_EXEC,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (mapping == MAP_FAILED) {
        printf("mmap failed: %s\n", strerror(errno));
        close(blob_fd);
        return 0;
    }

    ctx.base_load_paddr = ctx.base_load_vaddr = (Elf_Addr)(uintptr_t)mapping;

    status = el_load(&ctx, alloc_cb);
    if (status != EL_OK) {
        printf("el_load failed: %s (%d)\n", status_name(status), status);
        munmap(mapping, map_size);
        close(blob_fd);
        return 0;
    }

    status = el_relocate(&ctx);
    if (status != EL_OK) {
        printf("el_relocate failed: %s (%d)\n", status_name(status), status);
        munmap(mapping, map_size);
        close(blob_fd);
        return 0;
    }

    memset(&params, 0, sizeof params);
    params.font_path = argv[2];
    params.png_path = argv[3];
    params.text = argv[4];
    fill_api(&params.api);

    entry = (int (*)(struct blob_params *))((uintptr_t)mapping +
                                            (uintptr_t)ctx.ehdr.e_entry);
    entry(&params);

    munmap(mapping, map_size);
    close(blob_fd);
    return 0;
}
```

### `el_init`

```c
el_status el_init(el_ctx *ctx)
{
    ...
    if ((rv = el_pread(ctx, &ctx->ehdr, sizeof ctx->ehdr, 0)))
        return rv;

    if (!IS_ELF(ctx->ehdr))
        return EL_NOTELF;

    if (ctx->ehdr.e_ident[EI_CLASS] != ELFCLASS)
        return EL_WRONGBITS;

    if (ctx->ehdr.e_ident[EI_DATA] != ELFDATATHIS)
        return EL_WRONGENDIAN;

    if (ctx->ehdr.e_ident[EI_VERSION] != EV_CURRENT)
        return EL_NOTELF;

    if (ctx->ehdr.e_type != ET_EXEC && ctx->ehdr.e_type != ET_DYN)
        return EL_NOTEXEC;

    if (ctx->ehdr.e_machine != EM_THIS)
        return EL_WRONGARCH;

    if (ctx->ehdr.e_version != EV_CURRENT)
        return EL_NOTELF;
    ...
```

Проверки:

| Проверка | Ошибка |
|---|---|
| магия `7F 45 4C 46` | `EL_NOTELF` |
| класс 64 бит | `EL_WRONGBITS` |
| little-endian | `EL_WRONGENDIAN` |
| версия ELF | `EL_NOTELF` |
| тип `ET_EXEC`/`ET_DYN` | `EL_NOTEXEC` |
| архитектура x86-64 | `EL_WRONGARCH` |
| версия заголовка | `EL_NOTELF` |

Затем библиотека проходит по `PT_LOAD`:

```c
for (;;) {
    if ((rv = el_findphdr(ctx, &ph, PT_LOAD, &i)))
        return rv;

    if (i == (unsigned) -1)
        break;

    Elf_Addr phend = ph.p_vaddr + ph.p_memsz;
    if (phend > ctx->memsz)
        ctx->memsz = phend;

    if (ph.p_align > ctx->align)
        ctx->align = ph.p_align;

    i++;
}
```

`memsz` — максимальный конец сегмента в виртуальном пространстве. Для
PIE с `p_vaddr`, начинающимся с нуля, это и есть размер образа.

Если тип `ET_DYN`, ищется `PT_DYNAMIC`:

```c
if (ctx->ehdr.e_type == ET_DYN) {
    i = 0;
    if ((rv = el_findphdr(ctx, &ph, PT_DYNAMIC, &i)))
        return rv;
    if (i == (unsigned) -1)
        return EL_NODYN;
    ctx->dynoff  = ph.p_offset;
    ctx->dynsize = ph.p_filesz;
}
```

Без `PT_DYNAMIC` нельзя применить релокации. Blob, собранный без
`-pie`, мог бы не иметь этой секции — тогда `EL_NODYN`.

### `mmap`

```c
mapping = mmap(NULL, map_size, PROT_READ | PROT_WRITE | PROT_EXEC,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
```

- `NULL` — адрес выбирает ядро;
- `map_size` — `ctx.memsz`;
- `PROT_READ | PROT_WRITE | PROT_EXEC` — сразу RWX;
- `MAP_PRIVATE | MAP_ANONYMOUS` — приватная анонимная память, не
  связанная с файлом;
- `-1, 0` — файловый дескриптор и смещение не нужны.

Почему не `mmap` самого файла? Потому что:

- сегменты лежат по разным смещениям и с разными правами;
- между ними могут быть промежутки;
- BSS нужно обнулить;
- релокации требуют записи в память.

Анонимная память плюс копирование сегментов проще и понятнее.

Почему RWX? Так в примере `elfload` и так проще: после копирования и
релокаций сразу можно выполнять код, без `mprotect`. Минус — страницы
одновременно записываемые и исполняемые, это не лучшая практика
безопасности. Для лабораторной с доверенным blob допустимо.

### `base_load_paddr` и `base_load_vaddr`

```c
ctx.base_load_paddr = ctx.base_load_vaddr = (Elf_Addr)(uintptr_t)mapping;
```

Оба поля получают реальный адрес отображения. Дальше:

- физический адрес сегмента = `p_paddr + base_load_paddr`;
- виртуальный = `p_vaddr + base_load_vaddr`.

Для обычного PIE `p_paddr` и `p_vaddr` совпадают или близки, а
разделение нужно для архитектур, где это не так.

### `el_load`

```c
el_status el_load(el_ctx *ctx, el_alloc_cb alloc)
{
    Elf_Addr pdelta = ctx->base_load_paddr;
    Elf_Addr vdelta = ctx->base_load_vaddr;

    Elf_Phdr ph;
    unsigned i = 0;
    for (;;) {
        if ((rv = el_findphdr(ctx, &ph, PT_LOAD, &i)))
            return rv;

        if (i == (unsigned) -1)
            break;

        Elf_Addr pload = ph.p_paddr + pdelta;
        Elf_Addr vload = ph.p_vaddr + vdelta;

        char *dest = alloc(ctx, pload, vload, ph.p_memsz);
        if (!dest)
            return EL_ENOMEM;

        if ((rv = el_pread(ctx, dest, ph.p_filesz, ph.p_offset)))
            return rv;

        memset(dest + ph.p_filesz, 0, ph.p_memsz - ph.p_filesz);

        i++;
    }

    return rv;
}
```

Для каждого `PT_LOAD`:

1. Вычислить адрес назначения.
2. Позвать `alloc_cb`; в нашем случае он возвращает `vload`.
3. Прочитать `p_filesz` байт из файла по смещению `p_offset`.
4. Обнулить хвост от `p_filesz` до `p_memsz` — это BSS.

После этого в памяти лежит точная копия образа.

### `el_relocate`

```c
el_status el_relocate(el_ctx *ctx)
{
    if (ctx->ehdr.e_type != ET_DYN)
        return EL_OK;

    char *base = (char *) ctx->base_load_paddr;

    el_relocinfo ri;
    if ((rv = el_findrelocs(ctx, &ri, DT_RELA)))
        return rv;

    if (ri.entrysize != sizeof(Elf_RelA) && ri.tablesize) {
        return EL_BADREL;
    }

    size_t relacnt = ri.tablesize / sizeof(Elf_RelA);
    Elf_RelA *relatab = (Elf_RelA *)(base + ri.tableoff);
    for (size_t i = 0; i < relacnt; i++) {
        if ((rv = el_applyrela(ctx, &relatab[i])))
            return rv;
    }

    return rv;
}
```

`el_findrelocs` ищет в динамической секции три записи:

- `DT_RELA` — адрес таблицы;
- `DT_RELASZ` — размер таблицы;
- `DT_RELAENT` — размер одной записи.

Затем для каждой записи вызывается `el_applyrela`:

```c
el_status el_applyrela(el_ctx *ctx, Elf_RelA *rel)
{
    uint64_t *p = (uint64_t*) (rel->r_offset + ctx->base_load_vaddr);
    uint32_t type = ELF_R_TYPE(rel->r_info);

    switch (type) {
        case R_AMD64_NONE: break;
        case R_AMD64_RELATIVE:
            *p = rel->r_addend + ctx->base_load_vaddr;
            break;
        default:
            return EL_BADREL;
    }

    return EL_OK;
}
```

Для `R_X86_64_RELATIVE`:

```text
p = база + r_offset
*p = база + r_addend
```

`r_offset` — виртуальный адрес ячейки, `r_addend` — виртуальный адрес
цели. Оба сдвигаются на реальную базу.

Другие типы (`GLOB_DAT`, `JUMP_SLOT`) не поддерживаются. В нашем blob
их нет: все внешние символы разрешены на этапе компоновки, а
`-Bsymbolic` и version script не дают появиться динамическим
импортам. Если бы появились, загрузчик вернул бы `EL_BADREL`.

### Точка входа

```c
entry = (int (*)(struct blob_params *))((uintptr_t)mapping +
                                        (uintptr_t)ctx.ehdr.e_entry);
entry(&params);
```

`e_entry` — виртуальный адрес `blob_entry` (0x8040). Так как база
отображения соответствует виртуальному адресу 0, реальный адрес:

```text
mapping + e_entry
```

Приводим к указателю на функцию с одним аргументом и вызываем. На
x86-64 System V первый аргумент передаётся в `rdi`, поэтому
`blob_entry` получает указатель на `params`.

`entry` возвращает `int`, но загрузчик результат игнорирует: blob
всегда возвращает 0, а ошибки печатает сам.

### `fill_api`

```c
static void fill_api(struct host_api *api)
{
    memset(api, 0, sizeof *api);
    api->fopen = fopen;
    api->fclose = fclose;
    ...
    api->setjmp_fn = _setjmp;
    api->longjmp_fn = longjmp;
    api->errno_location = __errno_location;
    api->open_fn = (int (*)(const char *, int, mode_t))open;
    api->close_fn = close;
    api->read_fn = read;
    api->fcntl_fn = (int (*)(int, int, int))fcntl;
    api->fstat_fn = fstat;
    api->mmap_fn = mmap;
    api->munmap_fn = munmap;
    api->stderr_file = stderr;
    api->stdout_file = stdout;
    api->abort_fn = abort;
}
```

Это обычные адреса функций libc, взятые в процессе-загрузчике. Blob
вызывает их через указатели, поэтому ему не нужны ни PLT, ни
динамический загрузчик.

Приведение типов у `open` и `fcntl` нужно из-за вариативных
прототипов: в таблице упрощённые сигнатуры, а реальные функции
принимают `...`. Для используемых вызовов этого достаточно.

### `status_name`

```c
static const char *status_name(el_status status)
{
    switch (status) {
    case EL_OK:          return "OK";
    case EL_EIO:         return "read error";
    case EL_ENOMEM:      return "out of memory";
    case EL_NOTELF:      return "not an ELF file";
    case EL_WRONGBITS:   return "wrong ELF class";
    case EL_WRONGENDIAN: return "wrong byte order";
    case EL_WRONGARCH:   return "wrong architecture";
    case EL_WRONGOS:     return "wrong OS ABI";
    case EL_NOTEXEC:     return "not an executable";
    case EL_NODYN:       return "no dynamic section";
    case EL_BADREL:      return "bad relocation";
    default:             return "unknown error";
    }
}
```

Коды ошибок превращаются в понятные строки. `el_status` — это enum
из `elfload.h`.

### Почему загрузчик не ищет `main`

В примере из `elfload` иногда ищут символ `main` в таблице символов
и вызывают его. Наш загрузчик так не делает: он берёт `e_entry` из
ELF-заголовка. Это правильнее, потому что:

- `main` — соглашение C-программы, а не ELF;
- у blob может не быть `main` вообще;
- `e_entry` — это официальная точка входа, которую задаёт
  компоновщик.

Именно поэтому `blob_entry` не обязан называться `main`.

### Обработка ошибок

Каждый шаг проверяется:

```c
status = el_init(&ctx);
if (status != EL_OK) { ... return 0; }

status = el_load(&ctx, alloc_cb);
if (status != EL_OK) { ... return 0; }

status = el_relocate(&ctx);
if (status != EL_OK) { ... return 0; }
```

При ошибке освобождается то, что уже было выделено:

- `munmap(mapping, map_size)`;
- `close(blob_fd)`.

Загрузчик всегда возвращает 0, даже при ошибке. Это то же соглашение,
что и у приложения: не завершаться аварийно, а печатать сообщение.

## 11. Makefile изнутри

### Корневой Makefile

Файл:

- [`Makefile`](../Makefile)

Корневой файл ничего сам не компилирует. Он по очереди вызывает
Makefile в `zlib/`, `libpng/`, `freetype/`, `app/` и `elfloader/`.

### Граф целей

```text
make all
  ├── clean-bins          удаляет app-static, app-dynamic, app-blob
  ├── static
  │     zlib → libpng → freetype → app
  ├── dynamic
  │     те же каталоги, цель dynamic
  └── blob
        те же каталоги, цель blob, затем elfloader
```

Порядок каталогов фиксированный: libpng и FreeType линкуются с уже
собранным zlib. Готовые `libz.a`, `libz.so.1`, `libpng.a`, `libpng.so`,
`libfreetype.a` и `libfreetype.so` пишутся сразу в `build/`.

### Сборка zlib

`zlib/Makefile` перечисляет нужные `.c` и компилирует их одним
правилом `object_files/%.o: %.c`. Файлы `gz*.c` не входят: программа
не пользуется файловым gzip, а эти исходники тянут лишние вызовы libc
в blob.

Флаги одни и для архива, и для `.so`:

```text
-O2 -fPIC -fno-stack-protector -U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0
```

`-fPIC` нужен статической библиотеке тоже: она вшивается в PIE-blob.
`static` и `blob` собирают `build/libz.a` через `ar rcs`. `dynamic`
собирает `build/libz.so.1` и симлинк `build/libz.so`. `-MMD -MP`
записывает зависимости от заголовков.

### Сборка libpng

`libpng/Makefile` компилирует исходники записи и чтения PNG.
`pngtest.c` и SIMD-файлы из `arm/`, `intel/`, `mips/`, `powerpc/`
не входят. Заголовок `scripts/pnglibconf.h.prebuilt` копируется
правилом make в `libpng/object_files/pnglibconf.h`, в дерево
исходников он не пишется.

`libpng.so` линкуется так:

```text
gcc -shared -Wl,-soname,libpng.so -Wl,-rpath,'$ORIGIN' -lz -lm
```

`$ORIGIN` — каталог самой `libpng.so`. Рядом лежит `libz.so.1`,
поэтому `dlopen` находит zlib без `LD_LIBRARY_PATH`. `-lm` нужен
из-за `pow` и `floor`.

### Сборка FreeType

`freetype/Makefile` следует `docs/INSTALL.ANY`: один укрупнённый `.c`
на модуль из `include/freetype/config/ftmodule.h`, плюс `ftgzip.c` и
`ftlzw.c`. У каждого объекта своя строка зависимости, рецепт
компиляции общий: `object_files/%.o`.

Системный слой — `src/base/ftsystem.c`. Он открывает файл через
`fopen`. `builds/unix/ftsystem.c` не используется: ему нужен
`ftconfig.h`, который создаёт только `configure`.

`-DFT_CONFIG_OPTION_SYSTEM_ZLIB` заставляет `ftgzip.c` звать наш zlib,
а не встроенную копию. Иначе при линковке с `libz.a` совпадут имена
`inflate` и `crc32`. bzip2, встроенный PNG и harfbuzz в `ftoption.h`
уже выключены. `-std=gnu11` оставляет символ `strtol` обычным: при
стандарте C23 заголовки glibc подменяют его на `__isoc23_strtol`,
которого в blob нет.

`libfreetype.so` тоже получает `-lz -lm` и `rpath $ORIGIN`.

В `build/` лежат:

```text
build/libz.so         — симлинк на libz.so.1
build/libz.so.1
build/libz.a
build/libpng.so
build/libpng.a
build/libfreetype.so
build/libfreetype.a
```

Имена `libz.so.1`, `libpng.so` и `libfreetype.so` открывает
`app-dynamic` через `open_beside`.

### `app/Makefile`

Объектные каталоги:

```text
app/object_files/
  static/main.o
  static/funcs.o
  dynamic/main.o
  dynamic/funcs.o
  dynamic/dynload.o
  blob/main.o
  blob/funcs.o
  blob/host_shim.o
  blob/setjmp_stub.o
```

Три шаблонных правила, по одному на каталог. У static флаг
`-DMODE_STATIC`, у dynamic `-DMODE_DYNAMIC`, у blob `-DMODE_BLOB`.
`setjmp_stub.S` собирается отдельным правилом для `.S`. Лишний `-D`
на `dynload.c` и `host_shim.c` ничего не меняет: `MODE_DYNAMIC`
проверяют только `main.c` и `funcs.c`, `MODE_BLOB` — только `main.c`.

`-MMD -MP`:

- `-MMD` — создать `.d`-файл с зависимостями от заголовков;
- `-MP` — добавить фиктивные цели для заголовков, чтобы удаление
  заголовка не ломало make.

В конце:

```make
-include $(wildcard $(OBJDIR)/*/*.d)
```

`-include` не считает отсутствие файла ошибкой: при первой сборке
`.d` ещё нет.

### `elfloader/Makefile`

```make
SRCS := main.c elfload/elfload.c elfload/elfreloc_amd64.c
HDRS := ../app/host_api.h elfload/elfload.h elfload/elfarch.h elfload/elf.h

$(BUILD)/elfloader: $(SRCS) $(HDRS)
	@mkdir -p $(BUILD)
	gcc -D_GNU_SOURCE -Wall -Wextra -O2 -I../app -Ielfload \
		-o $@ $(SRCS) -lm
```

`-D_GNU_SOURCE` включает объявления `pread`, `mmap` и других
POSIX-функций. `-I../app` нужен, чтобы найти `host_api.h`.

### Инкрементная сборка

Make сравнивает время изменения целей и зависимостей. Поэтому:

- `touch app/funcs.c` → пересобирается `funcs.o` и перелинковывается
  `app-static`;
- `touch zlib/adler32.c` → zlib пересобирает `adler32.o`, обновляет
  `build/libz.a`, приложение перелинковывается;
- повторный `make static` без изменений ничего не делает.

Проверить:

```bash
touch app/funcs.c
make static
touch zlib/adler32.c
make static
make static
```

## 13. Диагностика

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `dlopen ... cannot open shared object file` | `.so` нет рядом с `app-dynamic` | `make dynamic` |
| `dlsym FT_New_Face failed` | библиотека не та или символ скрыт | проверить `nm -D build/libfreetype.so` и поиск `FT_New_Face` |
| `cannot open font` | неверный путь или шрифт не TTF | проверить путь, `file font.ttf` |
| `cannot create png` | нет прав на каталог | выбрать другой путь |
| `png write failed` | ошибка libpng при записи | проверить диск и путь |
| `out of memory` | слишком большой текст или мало памяти | уменьшить текст |
| `zlib 1.2.11` не совпадает с ожидаемым | загрузилась другая zlib | проверить `ls -l build/libz.so.1` |
| `el_init failed: not an ELF file` | передан не blob | передать `build/app-blob` |
| `el_init failed: wrong ELF class` | 32-битный blob | пересобрать под x86-64 |
| `el_init failed: no dynamic section` | blob собран без `-pie` | добавить `-pie` |
| `el_load failed: read error` | файл обрезан | пересобрать blob |
| `el_relocate failed: bad relocation` | в blob есть `GLOB_DAT`/`JUMP_SLOT` | проверить `--no-undefined`, `-Bsymbolic`, обёртки |
| `el_load failed: out of memory` | `ctx.memsz` слишком велик | проверить сегменты `readelf -lW` |
| blob падает с `SIGSEGV` | не хватает обёртки libc или неверная сигнатура в `host_api` | проверить `nm -u build/app-blob` до линковки, `--no-undefined` |
| blob падает с `SIGILL` (`ud2`) | `longjmp` до `host_install` | проверить порядок в `blob_entry` |
| `cannot read /proc/self/exe` | нет `/proc` | запускать на обычном Linux |
| `path to ... is too long` | слишком длинный путь | сократить путь |
| пустой PNG | текст пустой или шрифт не содержит глифов | проверить аргументы |

## 14. Ограничения

1. **Только x86-64 Linux.** `elfload` собран для `__amd64__`, а
   `setjmp_stub.S` написан для System V x86-64. На другой
   архитектуре нужны другие `elfreloc_*.c` и ассемблер.
2. **Только `R_X86_64_RELATIVE`.** Загрузчик не умеет `GLOB_DAT`,
   `JUMP_SLOT` и другие релокации. Текущий blob их не содержит, но
   при добавлении динамических импортов загрузка упадёт.
3. **Нет TLS.** Blob не настраивает thread-local storage. Если
   библиотека использует `__thread`, она не заработает. Текущие
   zlib/libpng/FreeType обходятся без этого, а `errno` идёт через
   `__errno_location`.
4. **Нет конструкторов.** `-nostdlib` означает, что `DT_INIT` и
   `DT_INIT_ARRAY` не выполняются. У текущих библиотек нет
   конструкторов, которым это было бы нужно. Если появится
   библиотека с `__attribute__((constructor))`, её инициализация не
   произойдёт.
5. **RWX-память.** Образ отображается с правами чтения, записи и
   исполнения. Это удобно, но небезопасно. Для учебной работы с
   доверенным blob допустимо; для недоверенного кода нужен
   `mprotect` по сегментам и проверка заголовков.
6. **Нет изоляции.** Blob выполняется в том же процессе, с теми же
   правами, что и загрузчик. Он может читать и писать любую память
   процесса. Это не sandbox.
7. **Текст — байты, не Unicode.** `text[i]` передаётся в
   `FT_Get_Char_Index` как `unsigned char`. UTF-8 кириллица
   разберётся на отдельные байты и нарисуется неправильно.
8. **Ограничение 200 символов.** `TEXT_LIMIT` защищает от слишком
   большого буфера, но длинный текст будет обрезан.
9. **Статическая версия не полностью статическая.** libc и libm
   остаются динамическими. Это соответствует заданию (статически
   компонуются три библиотеки), но `ldd` всё равно показывает
   зависимости.
10. **`load` у blob всегда ноль.** Реальная загрузка (mmap,
    копирование, релокации) происходит в `elfloader` до вызова
    `blob_entry` и не входит в измерение. `total` тоже считает
    только время работы blob, без времени загрузчика.
11. **`load` у static всегда ноль.** Динамический загрузчик уже
    отработал до `main`; измерение начинается позже.
12. **Один шрифт и один текст за запуск.** Программа не умеет
    переносить строки, выбирать начертание или рисовать несколько
    строк.
13. **Нет полноценной проверки blob.** `elfload` проверяет формат,
    но не проверяет, что сегменты не пересекаются, не выходят за
    `memsz` и не содержат опасных адресов. Для доверенного файла
    этого достаточно.
14. **`p_align` не используется.** Загрузчик берёт максимум
    `p_align`, но `mmap` выравнивает по странице. Если blob требует
    выравнивание больше страницы, это не будет соблюдено.

## 15. Как расширять

### Добавить функцию libc в blob

1. Добавить поле в `struct host_api`:

   ```c
   int (*isatty)(int fd);
   ```

2. Заполнить его в `fill_api`:

   ```c
   api->isatty = isatty;
   ```

3. Добавить обёртку в `host_shim.c`:

   ```c
   int isatty(int fd)
   {
       return (api && api->isatty) ? api->isatty(fd) : 0;
   }
   ```

4. Если имя конфликтует с макросом или asm-именем glibc, сделать
   `blob_isatty` и добавить `.set isatty, blob_isatty` в
   ассемблерный блок.
5. Пересобрать. `--no-undefined` покажет, если что-то забыто.

### Добавить библиотеку в blob

1. Собрать её статически с `-fPIC`.
2. Добавить `.a` в `LIBS` и в команду компоновки blob.
3. Проверить, какие внешние символы она требует:
   ```bash
   nm -u build/libnew.a
   ```
4. Для каждого символа добавить обёртку и поле в `host_api`.
5. Пересобрать и проверить:
   ```bash
   readelf -d build/app-blob | grep NEEDED
   readelf -rW build/app-blob | awk '/R_X86_64/{print $3}' | sort | uniq -c
   ```
   Должны остаться только `R_X86_64_RELATIVE`.

### Добавить библиотеку в dynamic

1. Добавить `open_beside("libnew.so")` в `load_libraries`.
2. Добавить указатели и `dlsym` для нужных функций.
3. Добавить `#define` в `dynload.h`.
4. Проверить порядок загрузки, если новая библиотека зависит от
   существующих.

### Поддержать UTF-8

Вместо побайтового прохода нужно декодировать кодовые точки:

```c
const unsigned char *p = (const unsigned char *)text;
while (*p) {
    FT_ULong cp;
    int len;
    /* UTF-8 decode: 1–4 байта */
    ...
    FT_UInt index = FT_Get_Char_Index(face, cp);
    ...
    p += len;
}
```

Ширину и рисование нужно считать по кодовым точкам, а не по байтам.
Тогда кириллица и другие языки будут работать.

### Сделать память W^X

Вместо `PROT_READ | PROT_WRITE | PROT_EXEC` можно:

1. Отобразить память как `RW`.
2. Загрузить сегменты и применить релокации.
3. Пройти по сегментам и выставить права:
   - `R` для read-only;
   - `R | X` для кода;
   - `R | W` для данных.
4. Вызвать `mprotect` для каждого диапазона.

Это требует аккуратной работы с границами страниц и запретом записи
в исполняемые страницы.

### Полностью статическая сборка

Для `app-static` можно добавить `-static`:

```bash
gcc -static -o build/app-static ... -lm
```

Но тогда нужно статически слинковать и glibc, а это тянет
`libnss`, `libpthread` и другие компоненты. Для задания это не
требуется: статически компонуются только три библиотеки.

### Дополнительное задание 6.2

6.2 сделано. У zlib, libpng и FreeType свои Makefile: список `.c`,
шаблонное правило для `.o`, `ar` для архива и `gcc -shared` для `.so`.
`./configure` не запускается. 6.1 (загрузчик под Windows) не делалось.

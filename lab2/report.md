2 ТЕОРЕТИЧЕСКИЕ СВЕДЕНИЯ

2.1 Этапы сборки программы

Сборка программы на языке C обычно включает четыре этапа: препроцессирование, компиляцию, ассемблирование и компоновку. На этапе препроцессирования подключаются заголовочные файлы, раскрываются макросы и выполняются директивы условной компиляции. На этапе компиляции исходный текст преобразуется в ассемблерный код, а затем ассемблер создаёт объектный файл. Объектный файл — это уже машинный код, но ещё не готовая программа: в нём могут оставаться ссылки на функции и данные из других файлов. Кроме кода и данных, объектный файл содержит таблицу символов и список мест, где при окончательной сборке нужно поправить адреса.

На последнем этапе работает компоновщик [8]. Его задача — собрать из объектных файлов одну программу и разрешить все ссылки на функции и данные. Если функция находится в статической библиотеке, компоновщик достаёт из неё нужный объектный файл и целиком включает его в программу. Если функция находится в разделяемой библиотеке, компоновщик не копирует её код, а записывает в программу имя библиотеки и имя нужной функции. Настоящий адрес функции становится известен только при запуске, когда библиотека уже загружена в память. Этим занимается динамический загрузчик.

Для автоматизации сборки используется утилита make и файл Makefile. Makefile описывает цели, зависимости и команды, которые нужно выполнить. Make сравнивает время изменения целей и их зависимостей и пересобирает только устаревшие файлы, что и обеспечивает инкрементную сборку.

2.2 Статическая компоновка

Статическая библиотека — это архив уже скомпилированных объектных файлов с расширением .a. Его можно представить как коробку с готовыми деталями: компоновщик берёт из неё только те детали, которые нужны программе, и вклеивает их в итоговый файл. Поэтому после сборки код библиотеки становится частью программы. Плюс в том, что программа не зависит от наличия этой библиотеки в системе при запуске. Минус — размер: каждая программа носит свою копию библиотеки, а при обновлении библиотеки программу нужно пересобирать.

В работе статически компонуются три библиотеки: libz.a, libpng.a и libfreetype.a. Стандартная библиотека C и математическая библиотека остаются динамическими: задание требует статической компоновки именно трёх указанных библиотек, а не полной статической сборки всей программы. Поэтому команда ldd для статической версии показывает libc и libm, но не показывает libz, libpng и libfreetype.

2.3 Динамическая компоновка

Разделяемая библиотека (shared library) — это отдельный файл с расширением .so, который существует независимо от программы. Например, libz.so.1, libpng.so и libfreetype.so. В отличие от .a, её код не вклеивается в бинарник. Программа хранит только имя библиотеки и имена нужных функций, а при запуске динамический загрузчик находит .so, загружает её в память и подставляет реальные адреса. Одна и та же библиотека может использоваться несколькими программами, поэтому в памяти обычно хранится одна копия, а сама программа получается меньше.

У разделяемой библиотеки есть короткое внутреннее имя — SONAME, например libz.so.1. По нему загрузчик понимает, что это та же самая библиотека, даже если файл лежит в другом каталоге или называется немного иначе. Список необходимых библиотек хранится в ELF в виде записей DT_NEEDED: это что-то вроде списка того, что нужно загрузить, который программа предъявляет загрузчику. Сами разделяемые библиотеки собирают как позиционно-независимый код с флагом -fPIC, чтобы их можно было загрузить по любому адресу и не привязываться к конкретному месту в памяти.

В лабораторной работе динамическая версия программы не только связывается с библиотеками, но и загружает их явно в начале main с помощью функций dlopen и dlsym. Это позволяет измерить время загрузки библиотек отдельно от времени работы программы и наглядно показать, что при запуске программы библиотек ещё нет в её образе. Функция dlopen открывает разделяемый объект, dlsym находит адрес нужной функции, а dlclose освобождает библиотеку; приёмы подмены функций в разделяемых библиотеках описаны в [9]. Флаг RTLD_NOW требует разрешить все символы сразу, а RTLD_GLOBAL делает символы библиотеки доступными для последующей загрузки других библиотек.

2.4 Формат ELF, PIE и релокации

Исполняемый файл в Linux имеет формат ELF [10]. У него есть заголовок с общими сведениями: тип файла, архитектура, точка входа. Кроме того, в файле есть таблица программных заголовков — что-то вроде карты загрузки: какие куски файла нужно положить в память и по каким адресам. Для загрузки важны сегменты PT_LOAD, а для динамической информации — сегмент PT_DYNAMIC. Поле e_entry — это адрес, с которого начнётся выполнение программы.

Позиционно-независимый исполняемый файл, или PIE, может быть загружен по произвольному адресу. Для этого код использует относительную адресацию, а все абсолютные адреса, зависящие от базы загрузки, описываются релокациями. Проще говоря, релокация — это запись «в этом месте лежит адрес, который нужно поправить после загрузки». В x86-64 наиболее распространена релокация R_X86_64_RELATIVE: по указанному смещению нужно записать значение «база загрузки плюс addend». Если в файле нет импортируемых символов, других релокаций может не быть.

В blob-версии используется именно такая схема: файл собирается как PIE с флагами -fPIE и -pie, но без стандартной библиотеки, с флагом -nostdlib. Точка входа задаётся явно и называется blob_entry. Файл не содержит PT_INTERP и не имеет записей DT_NEEDED, поэтому загрузить его обычным динамическим загрузчиком нельзя. Вместо этого библиотека elfload загружает сегменты PT_LOAD в подготовленную память, применяет относительные релокации и вызывает точку входа.

Поскольку у blob-файла нет своей стандартной библиотеки, все обращения к функциям libc должны быть заменены на вызовы через таблицу указателей. Загрузчик заполняет эту таблицу адресами функций своего процесса и передаёт её точке входа вместе с параметрами программы. Внутри blob-файла остаются небольшие обёртки, которые просто переходят по указателям из таблицы. Такой подход позволяет использовать статические библиотеки zlib, libpng и FreeType, не компонуя с ними libc.

2.5 Библиотеки zlib, libpng и FreeType

zlib [1] отвечает за сжатие данных по алгоритму DEFLATE. Формат PNG использует сжатие для хранения пиксельных данных, поэтому libpng вызывает zlib при записи файла. В программе zlib также вызывается явно: функция zlibVersion печатает версию библиотеки, чтобы было видно, что она действительно подключена, а не используется только косвенно через libpng.

libpng [2] предоставляет функции для формирования PNG-файла: создание структур, установка параметров изображения, запись строк и завершение файла. Программа использует RGB-изображение с глубиной 8 бит на канал, без интерлейсинга и со стандартным сжатием.

FreeType [3] загружает шрифт из файла TTF, позволяет выбрать размер символов, получить индекс глифа по коду символа, загрузить и отрисовать глиф. Каждый глиф возвращается в виде битмапа с покрытием, которое затем переносится в RGB-буфер изображения. В работе используется размер 48 пикселей, белый фон и серые символы, получающиеся из значений покрытия.

2.6 Makefile и инкрементная сборка

Файл Makefile [6, 7, 12] состоит из правил вида «цель: зависимости» и команд, которые выполняются для получения цели. Если цель новее всех своих зависимостей, make считает её актуальной и ничего не делает. Если какая-то зависимость изменилась, цель пересобирается. Для служебных целей, которые не соответствуют файлам, используется объявление .PHONY.

В проекте применяются переменные для путей и флагов, шаблонные правила для компиляции объектных файлов и автоматические переменные $@, $< и $^. Для отслеживания зависимостей от заголовочных файлов компилятор запускается с флагами -MMD -MP, которые создают файлы .d. Эти файлы подключаются директивой include, поэтому при изменении заголовка пересобираются все объектные файлы, которые его используют.

Корневой Makefile не дублирует правила сборки библиотек, а вызывает их штатные системы сборки: configure и make. Библиотеки собираются вне исходных каталогов, в build/obj, устанавливаются в build/prefix, после чего готовые .a и .so копируются в build. Такой подход позволяет сохранить исходные каталоги библиотек чистыми и использовать стандартные механизмы, которые уже содержат все необходимые зависимости и флаги.

3.2 Программа формирования PNG

Программа принимает три аргумента: имя файла шрифта, имя выходного PNG-файла и текст сообщения. Для static и dynamic используется точка входа main, для blob — точка входа blob_entry. Во всех случаях в начале работы вызывается clock_gettime, затем измеряется время загрузки, выполняется отрисовка и печатается общее время.

Фрагмент main.c, отвечающий за разбор аргументов и замеры времени:

int main(int argc, char **argv)
{
    struct timespec start;
    struct timespec loaded;
    struct timespec now;
    const char *program = (argc > 0 && argv[0]) ? argv[0] : "app";

    clock_gettime(CLOCK_MONOTONIC, &start);
    if (argc != 4) {
        printf("usage: %s font png text\n", program);
        print_span("load", &start, &start);
        print_span("total", &start, &start);
        return 0;
    }

#ifdef MODE_DYNAMIC
    if (!load_libraries()) {
        clock_gettime(CLOCK_MONOTONIC, &now);
        print_span("load", &start, &now);
        print_span("total", &start, &now);
        return 0;
    }
#endif

    clock_gettime(CLOCK_MONOTONIC, &loaded);
    print_span("load", &start, &loaded);
    render_png(argv[1], argv[2], argv[3]);
    clock_gettime(CLOCK_MONOTONIC, &now);
    print_span("total", &start, &now);

#ifdef MODE_DYNAMIC
    unload_libraries();
#endif
    return 0;
}

При неверном числе аргументов программа не завершается с ошибкой, а печатает подсказку и возвращает код 0. Если шрифт не найден, PNG-файл невозможно создать или библиотека не загружается, программа также печатает сообщение и возвращает код 0. Это соответствует требованию не завершать работу аварийно при любых аргументах командной строки.

Функция render_png выполняет следующие действия:

1. Инициализирует FreeType и загружает шрифт по указанному пути.
2. Устанавливает размер символов 48 пикселей.
3. Проходит по тексту, получает индекс каждого глифа и суммирует горизонтальные продвижения, чтобы вычислить ширину изображения.
4. Вычисляет высоту изображения по ascender и descender шрифта.
5. Выделяет RGB-буфер, заполняет его белым цветом и рисует каждый глиф с учётом его bitmap_left и bitmap_top.
6. Записывает буфер в PNG через libpng и zlib.

Ширина и высота изображения вычисляются по формулам:

W = PAD + сумма advance_i + PAD
H = ascent + descent + 2 * PAD

где PAD равен 8 пикселям, ascent и descent берутся из метрик шрифта, а advance_i — горизонтальное продвижение i-го глифа. Значения FreeType хранятся в формате 26.6: единица равна 1/64 пикселя, поэтому перед использованием выполняется сдвиг на 6 бит.

Фрагмент функции render_png:

int render_png(const char *font_path, const char *png_path, const char *text)
{
    FT_Library library = NULL;
    FT_Face face = NULL;
    unsigned char *image = NULL;
    int failed = 0;
    int count = 0;
    int width = PAD;
    int ascent;
    int descent;
    int height;
    int baseline;
    int pen_x = PAD;

    if (!font_path || !png_path || !text) {
        printf("render_png: missing argument\n");
        return -1;
    }

    printf("zlib %s\n", zlibVersion());

    if (FT_Init_FreeType(&library) != 0) {
        printf("FT_Init_FreeType failed\n");
        return -1;
    }
    if (FT_New_Face(library, font_path, 0, &face) != 0) {
        printf("cannot open font '%s'\n", font_path);
        failed = 1;
        goto done;
    }
    if (FT_Set_Pixel_Sizes(face, 0, FONT_PX) != 0) {
        printf("FT_Set_Pixel_Sizes failed\n");
        failed = 1;
        goto done;
    }

    while (text[count] != '\0' && count < TEXT_LIMIT)
        count++;

    ascent = (int)(face->size->metrics.ascender >> 6);
    descent = (int)(-(face->size->metrics.descender >> 6));
    if (ascent < 1)
        ascent = FONT_PX;
    if (descent < 0)
        descent = 0;
    height = ascent + descent + PAD * 2;
    baseline = PAD + ascent;

    for (int i = 0; i < count; i++) {
        FT_UInt index = FT_Get_Char_Index(face, (unsigned char)text[i]);
        if (index == 0 || FT_Load_Glyph(face, index, FT_LOAD_DEFAULT) != 0) {
            width += FONT_PX / 2;
            continue;
        }
        width += (int)(face->glyph->advance.x >> 6);
    }
    width += PAD;

    image = malloc((size_t)height * (size_t)width * 3);
    if (!image) {
        printf("out of memory\n");
        failed = 1;
        goto done;
    }
    memset(image, 0xFF, (size_t)height * (size_t)width * 3);

    for (int i = 0; i < count; i++) {
        FT_UInt index = FT_Get_Char_Index(face, (unsigned char)text[i]);
        int advance = FONT_PX / 2;
        if (index != 0 && FT_Load_Glyph(face, index, FT_LOAD_RENDER) == 0) {
            paint_glyph(image, width, height, pen_x, baseline, face->glyph);
            advance = (int)(face->glyph->advance.x >> 6);
            if (advance <= 0)
                advance = FONT_PX / 2;
        }
        pen_x += advance;
    }

    if (write_png(png_path, image, width, height) != 0)
        failed = 1;

done:
    free(image);
    if (face)
        FT_Done_Face(face);
    if (library)
        FT_Done_FreeType(library);
    return failed ? -1 : 0;
}

Функция paint_glyph переносит битмап глифа в RGB-буфер. Для каждого пикселя покрытия вычисляется значение 255 минус покрытие, поэтому полностью покрытый пиксель становится чёрным, а непокрытый остаётся белым. Такой способ даёт простой сглаженный текст без отдельного альфа-канала.

Функция write_png создаёт структуру libpng, устанавливает параметры изображения, формирует массив указателей на строки и вызывает png_write_image. Для обработки ошибок libpng используется setjmp и longjmp: если библиотека обнаружит ошибку, управление вернётся в точку setjmp, после чего структуры освобождаются, а функция возвращает признак ошибки.

Фрагмент write_png с обработкой ошибок:

static int write_png(const char *path, unsigned char *image, int width, int height)
{
    FILE *fp;
    png_structp png_ptr;
    png_infop info;
    png_bytep * volatile rows = NULL;

    fp = fopen(path, "wb");
    if (!fp) {
        printf("cannot create png '%s'\n", path);
        return -1;
    }

    png_ptr = png_create_write_struct(PNG_LIBPNG_VER_STRING, NULL, NULL, NULL);
    if (!png_ptr) {
        printf("png_create_write_struct failed\n");
        fclose(fp);
        return -1;
    }
    info = png_create_info_struct(png_ptr);
    if (!info) {
        printf("png_create_info_struct failed\n");
        png_destroy_write_struct(&png_ptr, NULL);
        fclose(fp);
        return -1;
    }

    if (setjmp(*png_set_longjmp_fn(png_ptr, longjmp, sizeof(jmp_buf)))) {
        printf("png write failed for '%s'\n", path);
        free(rows);
        png_destroy_write_struct(&png_ptr, &info);
        fclose(fp);
        return -1;
    }

    png_init_io(png_ptr, fp);
    png_set_IHDR(png_ptr, info, (png_uint_32)width, (png_uint_32)height, 8,
                 PNG_COLOR_TYPE_RGB, PNG_INTERLACE_NONE,
                 PNG_COMPRESSION_TYPE_DEFAULT, PNG_FILTER_TYPE_DEFAULT);

    rows = malloc((size_t)height * sizeof(png_bytep));
    if (!rows) {
        printf("out of memory\n");
        png_destroy_write_struct(&png_ptr, &info);
        fclose(fp);
        return -1;
    }
    for (int y = 0; y < height; y++)
        rows[y] = image + (size_t)y * (size_t)width * 3;

    png_write_info(png_ptr, info);
    png_write_image(png_ptr, rows);
    png_write_end(png_ptr, info);

    free(rows);
    rows = NULL;
    png_destroy_write_struct(&png_ptr, &info);
    if (fclose(fp) != 0) {
        printf("cannot close png '%s'\n", path);
        return -1;
    }
    return 0;
}

3.3 Статическая версия

Статическая версия build/app-static компонуется с архивами libfreetype.a, libpng.a и libz.a. Команда компоновки имеет следующий вид:

gcc -o build/app-static object_files/static/main.o object_files/funcs.o \
    build/libfreetype.a build/libpng.a build/libz.a -lm

Ключевой особенностью является то, что в команде указаны именно архивы .a, а не разделяемые библиотеки .so. Компоновщик включает в исполняемый файл только те объектные файлы, которые содержат нужные символы. В результате код FreeType, libpng и zlib оказывается внутри app-static.

Проверка зависимостей показывает, что libpng, libz и libfreetype в списке динамических зависимостей отсутствуют. При этом libc и libm остаются динамическими, что соответствует требованию статической компоновки именно трёх библиотек. Размер app-static составляет около 1,01 МБ, что значительно больше динамической версии, потому что код трёх библиотек находится внутри файла.

В статической версии время загрузки библиотек равно нулю: к моменту входа в main все три библиотеки уже являются частью образа программы. Значение load в выводе программы поэтому всегда равно 0.000000, а общее время total включает только инициализацию FreeType, отрисовку текста и запись PNG. По результатам контрольных запусков total составило примерно от 0,85 до 1,00 мс.

3.4 Динамическая версия

Динамическая версия build/app-dynamic линкуется только с библиотекой libdl, которая обеспечивает функции dlopen, dlsym и dlclose. Сами zlib, libpng и FreeType в команде компоновки не указываются. Вместо этого в начале main вызывается load_libraries, которая открывает три разделяемых объекта и находит нужные функции.

Фрагмент dynload.c, отвечающий за поиск библиотек рядом с исполняемым файлом:

static void *open_beside(const char *filename)
{
    char exe[PATH_MAX];
    char path[PATH_MAX];
    ssize_t length;
    char *slash;
    void *handle;

    length = readlink("/proc/self/exe", exe, sizeof exe - 1);
    if (length < 0) {
        printf("cannot read /proc/self/exe\n");
        return NULL;
    }
    exe[length] = '\0';
    slash = strrchr(exe, '/');
    if (!slash) {
        printf("cannot resolve path to %s\n", filename);
        return NULL;
    }
    *slash = '\0';
    if (snprintf(path, sizeof path, "%s/%s", exe, filename) >= (int)sizeof path) {
        printf("path to %s is too long\n", filename);
        return NULL;
    }

    handle = dlopen(path, RTLD_NOW | RTLD_GLOBAL);
    if (!handle)
        printf("dlopen %s: %s\n", path, dlerror());
    return handle;
}

Фрагмент load_libraries, показывающий порядок открытия библиотек и привязку функций:

libz = open_beside("libz.so.1");
libpng = libz ? open_beside("libpng.so") : NULL;
freetype = libpng ? open_beside("libfreetype.so") : NULL;
if (!libz || !libpng || !freetype) {
    unload_libraries();
    return 0;
}

ok &= bind(libz, "zlibVersion", &p_zlibVersion);
ok &= bind(freetype, "FT_Init_FreeType", &p_FT_Init_FreeType);
ok &= bind(freetype, "FT_New_Face", &p_FT_New_Face);
ok &= bind(libpng, "png_create_write_struct", &p_png_create_write_struct);
ok &= bind(libpng, "png_write_image", &p_png_write_image);

Функция load_libraries открывает библиотеки в порядке libz.so.1, libpng.so, libfreetype.so. Такой порядок важен потому, что libpng и libfreetype зависят от libz.so.1. Поскольку libz загружается первой и с флагом RTLD_GLOBAL, при загрузке остальных библиотек динамический загрузчик находит уже загруженную libz по её SONAME и не ищет её повторно.

После открытия библиотек функция bind вызывает dlsym для каждой нужной функции и сохраняет полученный адрес в соответствующем указателе. В заголовочном файле dynload.h эти указатели подменяют обычные имена функций с помощью директив #define. Благодаря этому funcs.c выглядит одинаково для статической и динамической сборок: в нём вызываются FT_New_Face, png_write_image и другие обычные имена, но в динамической сборке они раскрываются в обращения к указателям.

Проверка ldd показывает, что app-dynamic зависит только от libc, а libpng, libz и libfreetype в списке отсутствуют. При этом readelf -d для libpng.so и libfreetype.so показывает зависимость от libz.so.1, то есть эти библиотеки используют zlib совместно. Время загрузки в динамической версии составило примерно от 0,14 до 0,23 мс, а общее время — от 0,97 до 1,19 мс. Разница между total и load примерно соответствует времени отрисовки и записи PNG.

3.5 Blob-версия

Blob-версия build/app-blob собирается как позиционно-независимый ELF-файл без стандартной библиотеки. Команда компоновки содержит следующие ключевые флаги:

gcc -nostdlib -pie -fPIE \
    -Wl,-e,blob_entry -Wl,--no-dynamic-linker -Wl,--no-undefined \
    -Wl,-Bsymbolic -Wl,--version-script,blob.map \
    -o build/app-blob object_files/blob/main.o object_files/blob/funcs.o \
    object_files/blob/host_shim.o object_files/blob/setjmp_stub.o \
    build/libfreetype.a build/libpng.a build/libz.a -lgcc

Флаг -nostdlib запрещает автоматическую компоновку со стандартной библиотекой C. Флаги -pie и -fPIE обеспечивают позиционно-независимый код. Опция -Wl,-e,blob_entry задаёт точку входа, а -Wl,--no-dynamic-linker запрещает добавление интерпретатора динамического загрузчика. Опция -Wl,--no-undefined требует, чтобы все символы были разрешены на этапе компоновки, а -Wl,-Bsymbolic связывает внутренние обращения с определениями внутри blob-файла. Файл blob.map скрывает все символы, поэтому наружу ничего не экспортируется.

Проверка readelf показывает, что app-blob имеет тип DYN, то есть является PIE-файлом, а точка входа равна 0x8040. В динамической секции нет записи DT_NEEDED, а в таблице .dynsym нет экспортируемых символов. Символ blob_entry является локальным символом в таблице .symtab, его адрес совпадает с e_entry. В файле нет сегмента PT_INTERP, поэтому обычный динамический загрузчик не может его запустить.

Все обращения к libc внутри blob-файла заменены обёртками из host_shim.c. Каждая обёртка вызывает функцию из таблицы host_api, которую загрузчик заполняет адресами функций своего процесса. Например, обёртка fopen выглядит так:

FILE *fopen(const char *path, const char *mode)
{
    return (api && api->fopen) ? api->fopen(path, mode) : NULL;
}

Аналогично устроены обёртки для fread, fwrite, fclose, malloc, free, memcpy, memset, строковых функций, функций форматирования и математических функций. Для функций, которые в glibc объявлены с особыми именами или макросами, используются псевдонимы ассемблера: например, strtol, open, close, read, fcntl, fstat, mmap и munmap определены через .set.

FreeType в Unix-системах открывает файл шрифта не только через fopen, но и через системный вызов open, а также использует fstat и mmap. Поэтому в таблицу host_api добавлены указатели open_fn, close_fn, read_fn, fcntl_fn, fstat_fn, mmap_fn и munmap_fn. Без них статическая libfreetype.a внутри blob-файла не смогла бы загрузить шрифт.

Особое место занимает setjmp и longjmp. libpng использует setjmp для обработки ошибок. Если бы setjmp в blob-файле был реализован как обычная функция, возврат из longjmp произошёл бы не в тот кадр стека. Поэтому в setjmp_stub.S используется не вызов, а переход jmp на функцию _setjmp загрузчика. Тогда _setjmp запоминает адрес возврата в коде libpng, и longjmp возвращает управление именно туда. Фрагмент setjmp_stub.S:

_setjmp:
setjmp:
__sigsetjmp:
    movq host_setjmp_fn(%rip), %rax
    testq %rax, %rax
    jz 1f
    jmp *%rax
1:
    xorl %eax, %eax
    ret

Загрузчик заполняет host_api, передаёт структуру blob_params в точку входа, после чего blob-файл работает как обычная программа, но все внешние функции вызываются через таблицу указателей. Размер app-blob составляет около 1,01 МБ, поскольку три библиотеки вшиты в него статически.

3.6 Загрузчик ELF на основе elfload

Загрузчик build/elfloader построен на библиотеке erincandescent/elfload [4]. Исходники библиотеки лежат в elfloader/elfload, а elfloader/main.c содержит небольшую обёртку, которая связывает elfload с нашей таблицей функций libc и структурой blob_params.

Алгоритм работы загрузчика состоит из следующих шагов:

1. Открыть blob-файл и передать elfload callback для чтения через pread.
2. Вызвать el_init: библиотека читает ELF-заголовок, проверяет класс, порядок байтов, архитектуру и тип, находит сегменты PT_LOAD и PT_DYNAMIC, вычисляет размер образа и выравнивание.
3. Выделить память через mmap размером ctx.memsz с правами на чтение, запись и исполнение.
4. Записать адрес отображения в ctx.base_load_paddr и ctx.base_load_vaddr.
5. Вызвать el_load: библиотека читает сегменты PT_LOAD в память и обнуляет BSS.
6. Вызвать el_relocate: библиотека применяет релокации R_X86_64_RELATIVE. В текущей сборке их 1308.
7. Вычислить адрес точки входа как «база плюс ctx.ehdr.e_entry» и вызвать blob_entry с указателем на blob_params.
8. Освободить память через munmap и закрыть файл.

Фрагмент обёртки, показывающий основные вызовы:

el_ctx ctx;
memset(&ctx, 0, sizeof ctx);
ctx.pread = pread_cb;

el_init(&ctx);

mapping = mmap(NULL, ctx.memsz, PROT_READ | PROT_WRITE | PROT_EXEC,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
ctx.base_load_paddr = ctx.base_load_vaddr = (Elf_Addr)(uintptr_t)mapping;

el_load(&ctx, alloc_cb);
el_relocate(&ctx);

entry = (int (*)(struct blob_params *))((uintptr_t)mapping + ctx.ehdr.e_entry);
entry(&params);

munmap(mapping, ctx.memsz);

В реальном коде после каждого вызова проверяется el_status и печатается сообщение об ошибке. Библиотека elfload поддерживает только релокации R_AMD64_RELATIVE и R_AMD64_NONE. Для нашего blob этого достаточно: в нём нет импортируемых символов, нет DT_NEEDED, а все 1308 релокаций имеют тип R_X86_64_RELATIVE. Если бы в blob появились GLOB_DAT или JUMP_SLOT, загрузчик вернул бы ошибку EL_BADREL.

Для простоты, как в примере upstream, память отображается сразу с правами RWX. Это позволяет загрузить сегменты, применить релокации и сразу передать управление точке входа без отдельного mprotect. При необходимости можно добавить mprotect по сегментам, но для лабораторной это не требуется.

Запуск blob-версии выполняется командой:

./build/elfloader build/app-blob font.ttf out.png TRSPO

Загрузчик передаёт в blob_params пути к шрифту и PNG, текст сообщения и заполненную таблицу функций. Blob-файл печатает время загрузки, версию zlib и общее время, после чего загрузчик освобождает память. В текущей реализации используется библиотека elfload [4]; обёртка не ищет символ main, а использует адрес e_entry из ELF-заголовка.

3.7 Корневой Makefile и инкрементная сборка

Корневой Makefile выполняет роль диспетчера. Цели static, dynamic и blob сначала вызывают stage-libs, которая собирает zlib, libpng и FreeType, устанавливает их в build/prefix и копирует готовые библиотеки в build. Затем вызывается Makefile в каталоге app с нужной целью. Для blob дополнительно вызывается Makefile в каталоге elfloader.

Сборка библиотек выполняется их штатными средствами. Zlib конфигурируется с префиксом build/prefix и собирает как libz.a, так и libz.so.1. libpng конфигурируется после zlib и использует build/prefix для заголовков и библиотек. FreeType конфигурируется с параметрами --with-zlib=yes, --with-bzip2=no, --with-png=no и --with-harfbuzz=no, поэтому сжатые шрифты обрабатываются через уже собранный zlib, а лишние зависимости не подключаются.

Полная сборка с нуля командой make clean && make all завершается успешно. В логе сборки есть предупреждения zlib о старом стиле определения функций и несколько предупреждений FreeType; они относятся к исходникам библиотек и не влияют на результат. В исходных файлах программы и загрузчика предупреждений нет. Результат сборки показан на рисунке 5.

4 ВЫВОДЫ

В ходе лабораторной работы были изучены этапы сборки программы и особенности статической и динамической компоновки. Была разработана программа на языке C, которая с помощью FreeType загружает шрифт из TTF-файла, с помощью libpng и zlib формирует PNG-изображение с текстом и печатает время загрузки библиотек и общее время работы.

Были собраны три версии программы. Статическая версия включает libz.a, libpng.a и libfreetype.a в исполняемый файл и не требует этих библиотек при запуске. Динамическая версия загружает разделяемые библиотеки через dlopen и dlsym, поэтому время загрузки можно измерить отдельно; оно составило около 0,14–0,23 мс. Blob-версия собрана без стандартной библиотеки, имеет одну точку входа blob_entry, не содержит DT_NEEDED и загружается с помощью библиотеки elfload: обёртка отображает память, el_load читает сегменты PT_LOAD, el_relocate применяет релокации R_X86_64_RELATIVE, после чего обёртка передаёт точке входа структуру с параметрами и таблицей функций.

Все три версии дали одинаковый PNG-файл, что подтверждает корректность выбранной схемы. Инкрементная сборка была проверена: при изменении одного исходного файла пересобираются только связанные с ним объектные файлы и итоговый бинарник. Корневой Makefile собирает библиотеки, программу и загрузчик из исходного кода и поддерживает цели static, dynamic, blob, all и clean.

Ограничениями текущей реализации являются: обработка текста как последовательности байт без полноценного декодирования UTF-8; поддержка загрузчиком elfload только релокаций R_AMD64_RELATIVE; динамическая компоновка libc и libm в статической версии, что соответствует требованию статической компоновки только трёх библиотек, но не является полностью статической сборкой. Дополнительные задания 6.1 и 6.2 не выполнялись.

static double seconds_between(const struct timespec *a, const struct timespec *b)
{
    return (double)(b->tv_sec - a->tv_sec) +
           (double)(b->tv_nsec - a->tv_nsec) / 1000000000.0;
}

static void print_span(const char *label, const struct timespec *from,
                       const struct timespec *to)
{
    printf("%s: %.6f s\n", label, seconds_between(from, to));
}

#ifdef MODE_BLOB

int blob_entry(struct blob_params *params)
{

    struct timespec loaded;
    struct timespec now;

    if (!params || !params->font_path || !params->png_path || !params->text ||
        !params->api.vprintf)

    clock_gettime(CLOCK_MONOTONIC, &now);
    print_span("total", &start, &now);

}

static bool pread_cb(el_ctx *ctx, void *dest, size_t nb, size_t offset)
{
    ssize_t got;

    (void)ctx;
    got = pread(blob_fd, dest, nb, (off_t)offset);
    return got == (ssize_t)nb;
}

static void *alloc_cb(el_ctx *ctx, Elf_Addr phys, Elf_Addr virt, Elf_Addr size)
{
    (void)ctx;
    (void)phys;
    (void)size;
    return (void *)(uintptr_t)virt;
}

int main(int argc, char **argv)
{
    el_ctx ctx;
    el_status status;
    struct blob_params params;
    unsigned char *mapping;
    size_t map_size;
    int (*entry)(struct blob_params *);

    if (argc != 5) {
        printf("usage: %s blob font png text\n", argc > 0 ? argv[0] : "elfloader");
        return 0;
    }

    blob_fd = open(argv[1], O_RDONLY);
    if (blob_fd < 0) {
        printf("cannot open blob '%s': %s\n", argv[1], strerror(errno));
        return 0;
    }

    memset(&ctx, 0, sizeof ctx);
    ctx.pread = pread_cb;

    status = el_init(&ctx);
    if (status != EL_OK) {
        printf("el_init failed: %s (%d)\n", status_name(status), status);
        close(blob_fd);
        return 0;
    }

    if (ctx.memsz == 0) {
        printf("blob has no loadable segments\n");
        close(blob_fd);
        return 0;
    }

    map_size = (size_t)ctx.memsz;
    mapping = mmap(NULL, map_size, PROT_READ | PROT_WRITE | PROT_EXEC,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (mapping == MAP_FAILED) {
        printf("mmap failed: %s\n", strerror(errno));
        close(blob_fd);
        return 0;
    }

    ctx.base_load_paddr = ctx.base_load_vaddr = (Elf_Addr)(uintptr_t)mapping;

    status = el_load(&ctx, alloc_cb);
    if (status != EL_OK) {
        printf("el_load failed: %s (%d)\n", status_name(status), status);
        munmap(mapping, map_size);
        close(blob_fd);
        return 0;
    }

    status = el_relocate(&ctx);
    if (status != EL_OK) {
        printf("el_relocate failed: %s (%d)\n", status_name(status), status);
        munmap(mapping, map_size);
        close(blob_fd);
        return 0;
    }

    memset(&params, 0, sizeof params);
    params.font_path = argv[2];
    params.png_path = argv[3];
    params.text = argv[4];
    fill_api(&params.api);

    entry = (int (*)(struct blob_params *))((uintptr_t)mapping +
                                            (uintptr_t)ctx.ehdr.e_entry);
    entry(&params);

    munmap(mapping, map_size);
    close(blob_fd);
    return 0;
}
